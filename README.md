## 이 커리큘럼의 설계 철학

핵심 문장 하나로 요약됩니다.

> **"우리는 지금 속도를 쫓는 게 아니라, 공부를 할 수 있을 만큼의 VRAM을 쫓아야 합니다."**

이 커리큘럼은 "로컬에서 모델 돌려보기"에서 멈추지 않습니다. 목표는
**모델을 소비하는 사람 → 모델을 서빙·최적화하는 사람**으로 옮겨가는 것입니다.

그래서 순서가 중요합니다.

```
[Ollama로 돌려본다]  →  이건 앱 사용자
      ↓
[vLLM으로 서빙한다]  →  이건 인프라 엔지니어
      ↓
[커널을 고쳐본다]    →  이건 성능 엔지니어
```

각 단계는 **"체감"** 을 목표로 합니다. 논문을 읽어서 아는 게 아니라,
숫자가 눈앞에서 무너지고 메모리가 터지는 걸 직접 보면서 아는 것입니다.

# Phase 0. 준비 — 장비를 갖춘다

## 1단계. AI 가속기 장비를 구매합니다

### 원문 요지

> - **맥미니 사지 마세요.** 저렴하긴 하지만, 로컬 AI를 처음 공부하는 사람이 MLX 커널을 다룰 리가 없습니다.
> - **DGX 스파크 사지 마세요.** 데스크탑이 없으면 괜찮긴 한데 600만원이에요. 돈 많으면 고.
> - 저는 **RTX 3090 1–2대를 중고로** 구매하기를 추천합니다.
> - RTX 4090은 24GB의 동일 VRAM이니 무시, 5090은 32GB VRAM인데 가격이 700만원이니 패스.
> - **RTX 3090 2대라면 48GB의 VRAM을 200만원 언더로** 갖출 수 있습니다.
> - 텐스토렌트 Blackhole도 250만원 + 아주 좋은 성능 + 32GB VRAM 입니다만, 초보분들에게는 조금 난이도가 있으니 일단 기본기를 먼저 갖춥시다.

### 개념 보충: 왜 VRAM이 기준인가

로컬 LLM에서 GPU를 고르는 기준은 보통 **연산 성능(TFLOPS)이 아니라 VRAM 용량**입니다.
이유는 "모델이 VRAM에 안 들어가면 아예 못 돌아간다"는 이진적 제약 때문입니다.

VRAM은 크게 세 곳에 쓰입니다.

```
VRAM = [모델 가중치] + [KV 캐시] + [활성화값/작업 공간]
         ↑ 고정         ↑ 배치·컨텍스트에 비례   ↑ 상대적으로 작음
```

**모델 가중치 대략 계산법:**

| 정밀도 | 파라미터당 바이트 | 8B 모델 | 14B 모델 | 70B 모델 |
|---|---|---|---|---|
| BF16/FP16 | 2 B | 16 GB | 28 GB | 140 GB |
| FP8 / INT8 | 1 B | 8 GB | 14 GB | 70 GB |
| INT4 (Q4) | 0.5 B | 4 GB | 7 GB | 35 GB |

> 공식: `가중치 용량(GB) ≈ 파라미터 수(B) × 정밀도 바이트`

여기서 왜 24GB가 아니라 48GB를 노리는지가 보입니다.
24GB면 **8B BF16(16GB)은 되지만 KV 캐시 여유가 빠듯**하고, 14B BF16(28GB)은 아예 안 들어갑니다.
48GB가 되면 14B BF16 + 넉넉한 KV 캐시, 또는 32B급 양자화 모델까지 실습 범위에 들어옵니다.
**"양자화 안 한 원본 모델"을 돌릴 수 있어야 3단계의 정확도 비교 실습이 가능**하다는 점이 핵심입니다.

### 왜 맥미니를 말리는가 (보충)

Apple Silicon의 통합 메모리는 "64GB를 8만원 어치 전기로 돌린다"는 매력이 있지만,
이 커리큘럼의 목표와 어긋납니다.

| 항목 | NVIDIA (CUDA) | Apple (MLX/Metal) |
|---|---|---|
| vLLM / TensorRT-LLM / SGLang | ✅ 1급 지원 | ❌ 사실상 불가 |
| Triton 커널 작성 | ✅ | ❌ |
| LoRA 학습 (bitsandbytes, unsloth) | ✅ | 제한적 |
| 학습 자료 / 예제 | 압도적 | 적음 |

즉 **14–17단계(커널·저수준)에 도달할 수 없는 장비**입니다.
원문의 "그냥 SSH 발사대입니다"(20단계)라는 표현이 이 뜻입니다.

### 실습 체크리스트

- [ ] **전원 확인**: RTX 3090은 카드당 350W. 2대면 GPU만 700W → **최소 1000W, 권장 1200W+ PSU**
- [ ] **PCIe 슬롯/공간**: 3090은 2.5~3슬롯 두께. 라이저 케이블 또는 여유 있는 케이스 필요
- [ ] **NVLink 브릿지** (댓글 팁): 3090 2대 구성 시 GPU 간 대역폭 확보용. 9단계 Tensor Parallel 실습에서 체감됨
- [ ] **쿨링**: 2장을 붙여 꽂으면 위쪽 카드가 아래 카드 열을 먹습니다. 블로워형/수랭 또는 슬롯 간격 확보
- [ ] 드라이버 + CUDA Toolkit 설치, `nvidia-smi`로 2장 모두 인식 확인

> 💡 댓글의 팁: *"3090 2대 구매하실 때엔 전력 체크 잘 하시고 nvlink 브릿지도 같이 구매하시기"*

> ⚠️ 중고 3090 구매 시: 채굴 이력 카드는 VRAM 발열/서멀패드 열화 이슈가 흔합니다.
> 구매 후 `gpu-burn` 등으로 장시간 부하 테스트를 걸어 VRAM 온도(105°C 근처면 위험)를 확인하세요.

### 체크포인트

`nvidia-smi`가 GPU 전부를 정상 인식하고, 풀로드 30분을 온도 throttling 없이 버틴다.

# Phase 1. 첫 접촉 — 돌려보고, 재보고, 무너지는 걸 본다

## 2단계. Ollama를 설치해서 간단한 모델을 돌려봅니다

### 원문 요지

> - 8B, 14B 등 작은 모델 위주로 돌려봅니다.
> - 그리고, **MMLU Pro, HumanEval 등 모델의 정확도를 판단하는 evaluation을 하는 방법**을 익힙니다.
> - GPT / Opus 에게 물어보면 스크립트를 짜줄 겁니다.

### 개념 보충: Ollama의 역할과 한계

Ollama는 `llama.cpp` 위에 씌운 사용성 래퍼입니다. 장점은 **1분 안에 모델이 돌아간다**는 것.
`ollama run qwen3:8b` 한 줄로 끝납니다.

하지만 이 커리큘럼에서 Ollama는 **"목적지가 아니라 출발점"** 입니다.
- 기본값이 대체로 4bit 양자화 → 사용자가 정확도 손실을 모르고 씀
- 배치/스케줄링 제어권이 거의 없음 → 7단계 실습 불가
- 그래서 4단계에서 **"Ollama를 지운다"** 는 지시가 나옵니다

### 개념 보충: 왜 벤치마크부터 배우는가

이게 이 커리큘럼의 가장 영리한 부분입니다.
**"측정 도구를 먼저 손에 쥔다."** 측정할 수 없으면 3단계 이후 모든 실습이 "느낌"으로 끝납니다.

두 축을 나눠서 봐야 합니다.

| 축 | 재는 것 | 대표 지표 |
|---|---|---|
| **품질(Quality)** | 모델이 얼마나 똑똑한가 | MMLU Pro, HumanEval, GSM8K |
| **성능(Performance)** | 모델이 얼마나 빠른가 | TTFT, TPOT (→ 6단계) |

- **MMLU Pro**: 14개 분야 12,000여 개 객관식 문제. 기존 MMLU의 포화·오답 문제를 개선한 버전.
  선택지가 10개로 늘어 찍기 확률이 낮고, 추론 단계가 깊어 양자화 손상이 잘 드러납니다.
  → **일반 지식/추론 능력** 측정
- **HumanEval**: 164개 파이썬 함수 작성 문제. 생성한 코드를 실제로 실행해 테스트를 통과하는지 봅니다.
  지표는 `pass@k` (k번 시도 중 하나라도 통과할 확률).
  → **코드 생성 능력** 측정. 채점이 자동·객관적이라 비교에 좋습니다.

### 실습

```bash
# 1. Ollama 설치 및 모델 실행
curl -fsSL https://ollama.com/install.sh | sh
ollama run qwen3:8b

# 2. OpenAI 호환 API로 호출 (평가 스크립트가 붙을 지점)
curl http://localhost:11434/v1/chat/completions \
  -H "Content-Type: application/json" \
  -d '{"model":"qwen3:8b","messages":[{"role":"user","content":"안녕"}]}'
```

평가 하네스는 직접 짜기보다 기성품을 쓰는 게 빠릅니다.
- `lm-evaluation-harness` (EleutherAI) — MMLU Pro 등 표준 벤치마크 다수
- `evalplus` / `bigcode-evaluation-harness` — HumanEval 계열

> 💡 원문대로 LLM에게 "Ollama의 OpenAI 호환 엔드포인트에 붙는 MMLU Pro 평가 스크립트를 짜줘"라고
> 요청해서 직접 만들어보는 것도 좋습니다. **평가 루프의 구조(프롬프트 포맷 → 파싱 → 채점)를
> 손으로 한 번 만들어보는 경험**이 3단계·16단계에서 계속 쓰입니다.

### 체크포인트

동일한 스크립트로 두 개 이상의 모델 정확도를 재현 가능하게 뽑을 수 있다.
(= 나중에 "양자화 전/후"를 같은 자로 잴 수 있다)

## 3단계. Ollama에서 여러 양자화 모델의 정확도를 비교해봅니다

### 원문 요지

> - 같은 모델이지만, **모델 가중치의 소수점 길이를 바꿔서** 성능을 조절할 수 있습니다.
> - 풀 모델(BF16)에 비해, 양자화된 모델(Q4_K_M, Q8_0, NVFP4) 등은 용량도 훨씬 작고, 정확도도 떨어집니다.
> - 풀 모델 vs 양자화 모델의 정확도를 MMLU Pro, HumanEval을 통해서 비교합니다.
> - **"양자화할수록 모델 정확도가 처참하게 떨어지는 걸 체감합니다."**

### 개념 보충: 양자화란 무엇인가

모델 가중치는 그냥 숫자 수십억 개입니다. 그 숫자 하나를 **몇 비트로 표현할지**를 바꾸는 것이 양자화입니다.

```
BF16:  0.13476562  (16비트, 2바이트)   ← 원본
INT8:  0.1348      ( 8비트, 1바이트)   ← 거의 동일
INT4:  0.125       ( 4비트, 0.5바이트) ← 눈에 띄게 뭉개짐
```

비유하면 **JPEG 압축률**입니다. 품질 100 → 80은 거의 티가 안 나지만, 20까지 내리면 뭉개집니다.
차이는 이미지는 "보기 흉해지는" 정도지만, LLM은 **추론 사슬 중간에서 틀리면 답 전체가 무너진다**는 것입니다.

**포맷 이름 읽는 법:**

| 표기 | 뜻 |
|---|---|
| `Q8_0` | 8비트, 스케일 하나(`_0`)를 블록마다 적용. 손실 거의 없음 |
| `Q4_K_M` | 4비트, **K-quant** 방식, **M**edium. 블록별로 다른 스케일 + 중요 레이어는 더 높은 비트 유지 |
| `Q4_0` | 4비트, 단순 방식. `Q4_K_M`보다 품질 낮음 |
| `FP8` | 부동소수점 8비트. **Ada(4090) / Hopper 이후** 하드웨어 가속 |
| `NVFP4` | 부동소수점 4비트. **Blackwell(5090)부터** 하드웨어 가속 |

핵심 직관: **같은 4비트라도 "어디에 정밀도를 쓸지" 배분 전략에 따라 품질이 크게 달라집니다.**
이 아이디어를 극단까지 밀면 16단계의 레이어별 양자화(GPTQ/AWQ)가 됩니다.

### 실습

동일 모델의 여러 양자화 버전을 받아 2단계 스크립트로 비교합니다.

```bash
ollama pull qwen3:8b-fp16      # 원본급
ollama pull qwen3:8b-q8_0      # 8비트
ollama pull qwen3:8b-q4_K_M    # 4비트
ollama pull qwen3:8b-q3_K_S    # 3비트 (무너지는 지점 관찰용)
```

결과를 표로 정리하세요. 이 표가 이 커리큘럼의 첫 산출물입니다.

| 양자화 | 파일 크기 | VRAM 사용 | MMLU Pro | HumanEval | 토큰/초 |
|---|---|---|---|---|---|
| FP16 | | | | | |
| Q8_0 | | | | | |
| Q4_K_M | | | | | |
| Q3_K_S | | | | | |

### 체크포인트

**"메모리를 절반 아끼면 정확도는 얼마를 내주는가"** 를 자기 숫자로 말할 수 있다.
그리고 어느 비트 수부터 급격히 무너지는지(보통 3~4bit 경계) 직접 봤다.

> 💡 관찰 포인트: 양자화 손상은 **작은 모델일수록, 추론이 긴 과제일수록** 심하게 나타납니다.
> 70B Q4는 멀쩡한데 3B Q4는 무너지는 걸 보면 "파라미터 수가 손상 여유(redundancy)"라는 감각이 생깁니다.

# Phase 2. 서빙 기초 — Ollama를 버리고 엔진 내부로

## 4단계. Ollama를 지우고 vLLM을 설치합니다

### 원문 요지

> 이제 **모델 서빙과 인퍼런스 최적화**로 넘어갑니다.

### 개념 보충: Ollama와 vLLM은 무엇이 다른가

| | Ollama (llama.cpp) | vLLM |
|---|---|---|
| 대상 | 개인 1인 사용 | 다중 사용자 프로덕션 서빙 |
| 핵심 기술 | GGUF 양자화, CPU 오프로딩 | **PagedAttention, Continuous Batching** |
| 동시 요청 | 사실상 순차 | 수십~수백 동시 처리 |
| 제어권 | 거의 없음 | 배치/캐시/병렬화 전부 노출 |

**"지운다"는 지시의 의미**: Ollama를 남겨두면 편해서 계속 씁니다.

## 5단계. vLLM을 소스 빌드 합니다

### 원문 요지

> - 소스 빌드 하고, **prefill / decode 단계에서 각각 디버깅을 걸어서** 모델 추론을 돌려봅니다.
> - **Prefill**은 쉽게 얘기하자면, 유저의 요청을 기억에 담아두고 사전에 처리해두는 겁니다.
> - **Decode**는 쉽게 얘기하자면, LLM의 답변을 한 단어씩 만들어내는 과정입니다.
> - Prefill에 걸리는 시간이 이 정도구나, Decode에 걸리는 시간이 이 정도구나, 를 우선 감으로 체감합니다.

### 개념 보충: Prefill vs Decode — LLM 추론의 두 얼굴

이건 로컬 LLM 이해의 **가장 중요한 분기점**입니다. 이 둘은 성격이 완전히 다릅니다.

```
사용자: "다음 코드를 리뷰해줘: (2000 토큰짜리 코드)"

┌─ PREFILL ─────────────────────────────────┐
│ 입력 2000 토큰을 "한꺼번에" 처리          │
│ → 큰 행렬 × 큰 행렬 연산                  │
│ → GPU 연산 유닛이 포화 = Compute-bound    │
│ → 결과: KV 캐시 생성 + 첫 토큰 1개        │
└───────────────────────────────────────────┘
                    ↓
┌─ DECODE ──────────────────────────────────┐
│ 토큰 1개 → 다음 토큰 1개, 반복 (500회)    │
│ → 작은 벡터 × 큰 가중치 행렬              │
│ → 매번 모델 전체를 VRAM에서 읽어옴        │
│ → 메모리 대역폭이 병목 = Memory-bound     │
└───────────────────────────────────────────┘
```

| | Prefill | Decode |
|---|---|---|
| 처리 단위 | 입력 전체 병렬 | 토큰 1개씩 순차 |
| 병목 | **연산 성능** (TFLOPS) | **메모리 대역폭** (GB/s) |
| 시간 복잡도 | 입력 길이의 **제곱** (attention) | 출력 길이에 **선형** |
| 대응 지표 | TTFT | TPOT |

**여기서 나오는 실전 통찰:**
- Decode가 메모리 대역폭 병목이라서 → **양자화가 속도를 올린다** (읽을 바이트가 줄어듦)
- Decode가 메모리 병목이라서 → **배치를 키워도 토큰/초가 크게 안 떨어진다** (7단계에서 확인)
- Prefill과 Decode의 성격이 달라서 → **분리해서 다른 GPU에 맡기는** 기법이 등장 (15단계 P/D disaggregation)
- 3090이 "속도는 3090, 용량은 48GB"인 게 괜찮은 이유도 여기 있습니다. Decode는 대역폭 게임입니다.

## 6단계. LLM 성능 벤치마크 측정법을 익힙니다

### 원문 요지

> **"TTFT, TPOT 을 측정하는 방법을 익힙니다."**
>
> - **TTFT**는 유저의 요청이 들어간 순간부터, 첫 단어가 나올 때까지의 시간을 의미합니다.
>   TTFT가 짧은 모델은, 엔터를 치는 순간 답변이 나옵니다. TTFT가 느린 모델은, 엔터를 치고 커피 한 잔 마시고 와도 답변이 안 나옵니다.
> - **TPOT**은 단어 생성 속도입니다. TPOT이 느린 모델은, 달팽이 기어가듯 한 단어 한 단어 만들어냅니다.
>   TPOT이 빠른 모델은, 순식간에 답변을 완성합니다.
> - TPOT의 역수(i.e. 1/TPOT)이 우리가 흔히 얘기하는 **토큰 생성 속도**입니다.
> - **TPOT이 30 이상이 되면 꽤나 챗봇으로 쓸만합니다.**

### 개념 보충: 4개의 지표

```
요청 전송 ─────┬──────────────────────────────────────→ 완료
               │
        [TTFT] │←─ 첫 토큰까지 (= Prefill 시간)
               │
               └─[TPOT][TPOT][TPOT]... ←─ 토큰 사이 간격 (= Decode 시간)

E2E Latency = TTFT + TPOT × (출력 토큰 수 - 1)
```

| 지표 | 정의 | 단위 | 결정 요인 |
|---|---|---|---|
| **TTFT** | Time To First Token | ms | Prefill = 입력 길이, 연산 성능 |
| **TPOT** | Time Per Output Token | ms/token | Decode = 메모리 대역폭, 모델 크기 |
| **Throughput** | 서버 전체 토큰 처리량 | tokens/s | 배치 크기, KV 캐시 여유 |
| **Goodput** | SLO를 만족한 요청만 센 처리량 | req/s | 위 전부 |

> 📌 용어 정리: 원문의 **"TPOT이 30 이상"** 은 문맥상 **1/TPOT, 즉 토큰 생성 속도 30 tok/s 이상**을 뜻합니다.
> TPOT 자체는 ms 단위이므로 30 tok/s ≈ **TPOT 33ms**입니다.
> 실무에서 `tok/s`와 `TPOT(ms)`를 혼용하는 경우가 많으니, 항상 **단위를 확인**하는 습관을 들이세요.

**체감 기준선 (참고):**

| 토큰 생성 속도 | 체감 |
|---|---|
| ~5 tok/s | 읽기보다 느림. 답답함 |
| ~10 tok/s | 느린 타이핑. 참을 수는 있음 |
| ~20 tok/s | 사람이 읽는 속도와 비슷 |
| **30+ tok/s** | 쾌적. 챗봇으로 쓸 만함 ← 원문 기준 |
| 100+ tok/s | 순식간. 에이전트/코드 생성에 적합 |

**TTFT 기준선:** 대화형은 200ms 이하가 목표, 1초를 넘으면 눈에 띄게 답답합니다.

### 개념 보충: 왜 처리량과 지연시간은 서로 싸우는가

이게 서빙 최적화의 근본 긴장입니다.

```
배치를 키우면 →  Throughput ↑↑  (GPU를 알차게 씀)
              →  TPOT ↑ (개별 사용자는 느려짐)
              →  KV 캐시 사용량 ↑↑ (메모리 압박)
```

그래서 "빠르다"는 말이 애매합니다. **"누구에게 빠른가"** 를 항상 물어야 합니다.
- 챗봇 = 개인 지연시간(TTFT/TPOT)이 왕
- 배치 처리/에이전트 = 전체 처리량이 왕

# Phase 3. 서빙 최적화 — 메모리와 처리량의 줄다리기

## 7단계. Batch를 1, 2, 4, 8, 16, 32 로 늘려봅니다

### 원문 요지

> - Batch는 LLM 서버가 동시에 처리할 수 있는 요청 수를 의미합니다 (쉽게 얘기해서).
> - Batch가 1이라면, 5명이 동시에 요청했을 때 순차적으로 처리합니다. Batch가 6이라면, 6명이 동시에 요청했을 때 동시에 처리해서 동시에 답변합니다.
> - Agentic AI + subagent 생각한다면, batch는 커야 좋습니다. 근데 막상 키워보면 **메모리를 엄청나게 먹는다**는 걸 알게 됩니다.
> - **"여기서 KV 캐시에 대한 개념을 익히고, KV 캐시 용량을 계산하는 방법을 익힙니다."**
> - 이후 vLLM의 소스코드를 뜯어보면서 **Continuous batching** 개념을 익힙니다. 쉽게 얘기하자면 유저 요청 수에 따라 batch 수를 유연하게 조정할 수 있는 기능입니다.
> - 이걸 위한 **Paged Attention** 커널도 확인하고, 왜 필요한지 이해합니다.

### 개념 보충 ①: KV 캐시 — 로컬 LLM 메모리의 진짜 주인공

Attention은 매 토큰 생성마다 **이전 모든 토큰의 Key/Value 벡터**를 참조합니다.
매번 다시 계산하면 낭비이므로 저장해둡니다. 이게 KV 캐시입니다.

> 비유: 소설을 이어 쓰는 작가. 새 문장을 쓸 때마다 앞부분을 처음부터 다시 읽을 순 없으니
> 요약 노트를 옆에 펼쳐둡니다. 그 노트가 KV 캐시입니다. **대화가 길어지면 노트도 두꺼워집니다.**

**계산 공식 (반드시 손으로 한 번 계산해볼 것):**

```
KV 캐시 크기 = 2 × L × H_kv × D_head × S × B × precision_bytes

  2          : Key와 Value 두 개
  L          : 레이어 수
  H_kv       : KV 헤드 수 (GQA면 쿼리 헤드보다 적음)
  D_head     : 헤드 차원
  S          : 시퀀스 길이 (컨텍스트)
  B          : 배치 크기 (동시 요청 수)
  precision  : FP16 = 2 bytes
```

**예시 — Llama-3-8B (L=32, H_kv=8, D_head=128, FP16):**

```
토큰 1개당 = 2 × 32 × 8 × 128 × 2 bytes = 131,072 bytes ≈ 128 KB

컨텍스트 8192, 배치 1  →  128 KB × 8192       ≈  1 GB
컨텍스트 8192, 배치 32 →  128 KB × 8192 × 32  ≈ 32 GB   ← 24GB GPU 사망
```

**여기서 "메모리를 엄청나게 먹는다"의 정체가 드러납니다.**
가중치는 16GB로 고정인데, KV 캐시는 `배치 × 컨텍스트`로 곱셈으로 늘어납니다.

> 💡 **GQA(Grouped Query Attention)** 가 왜 중요한지도 여기서 보입니다.
> H_kv를 쿼리 헤드의 1/4, 1/8로 줄이면 KV 캐시가 그대로 1/4, 1/8이 됩니다.
> 최신 모델이 전부 GQA/MLA를 쓰는 건 품질 문제가 아니라 **서빙 경제성** 문제입니다.

### 개념 보충 ②: Continuous Batching — 왜 "정적 배치"가 낭비인가

```
[Static Batching]  4개 요청을 묶어 처리, 전부 끝날 때까지 대기
요청A ████████████████████ (긴 답변)
요청B ████░░░░░░░░░░░░░░░░ ← 끝났는데 GPU 자리를 잡고 놀고 있음
요청C ██████░░░░░░░░░░░░░░ ← 낭비
요청D ███░░░░░░░░░░░░░░░░░ ← 낭비

[Continuous Batching]  끝난 자리에 대기 중인 요청을 즉시 투입
요청A ████████████████████
요청B ████▓▓▓▓▓▓▓▓ (요청E 투입)
요청C ██████▓▓▓▓▓▓▓▓ (요청F 투입)
요청D ███▓▓▓▓▓▓ (요청G 투입)
```

토큰 하나 생성할 때마다(iteration 단위) 스케줄러가 배치 구성을 다시 짭니다.
그래서 **iteration-level scheduling**이라고도 합니다. 실측 처리량이 수 배에서 20배 이상까지 올라갑니다.

### 개념 보충 ③: PagedAttention — OS의 가상 메모리를 KV 캐시에 적용

Continuous Batching을 하려면 **"요청이 수시로 들어오고 나가는" 메모리 관리**가 필요합니다.
그런데 KV 캐시를 요청별로 연속된 큰 덩어리로 잡으면:

- 요청이 실제로 얼마나 길어질지 모르니 **최대 길이로 미리 예약** → 대부분 안 씀 (내부 단편화)
- 요청이 들어오고 나가며 메모리에 구멍이 생김 → 큰 덩어리를 못 잡음 (외부 단편화)
- 논문 보고에 따르면 이 낭비가 **60~80%** 에 달했습니다

PagedAttention은 OS의 페이징을 그대로 빌려옵니다.

```
[연속 할당]  요청A: [████████░░░░░░░░░░░░░░░░]  ← 예약만 하고 못 쓰는 공간
[페이지 할당] 요청A: [블록7][블록2][블록9][블록4]  ← 물리적으로 흩어져도 OK
                     ↑ 블록 테이블이 논리→물리 매핑을 관리
```

- 고정 크기 블록(예: 16토큰)으로 쪼개 필요할 때만 할당 → 낭비를 **4% 이하**로 줄임
- 부수 효과가 강력합니다: **블록 공유(Copy-on-Write)**
  - 같은 시스템 프롬프트를 쓰는 요청 100개 → 프롬프트 부분 KV 블록 1벌만 저장
  - 이게 **Prefix Caching**이고, 에이전트 워크로드에서 TTFT를 극적으로 줄입니다
  - 이 아이디어를 트리 구조로 일반화한 게 **Radix Attention** (→ 15·20단계 SGLang)

### 실습

```bash
# 배치 상한을 바꿔가며 서버를 띄우고, 매번 6단계 벤치마크를 돌립니다
for n in 1 2 4 8 16 32; do
  vllm serve Qwen/Qwen3-8B --max-num-seqs $n --max-model-len 8192 &
  # ... vllm bench serve 실행 ...
done
```

| max-num-seqs | KV 캐시 (GB) | Mean TTFT | Mean TPOT | Throughput (tok/s) |

| 1 | | | | |

- 손 계산한 KV 캐시 값과 vLLM 기동 로그의 `GPU KV cache size`를 **대조**하세요

- `--enable-prefix-caching` 켜고 같은 프롬프트를 반복 요청 → TTFT 급감 확인

## 8단계. Max sequence length를 늘려봅니다

### 원문 요지

> - Context length와 거의 동일한 의미를 가집니다. **LLM의 단기 기억력**에 대한 설정 값입니다.
> - **"4096, 8192, 16384, 32768로 올릴수록 얼마나 긴 내용까지 제대로 기억하는지 확인해봅니다. 동시에 얼마나 메모리를 많이 먹는지 확인해봅니다."**
> - **KV 캐시는 linear하게 늘어나는데 Attention 연산은 quadratic하게 늘어나는 것**도 확인합니다.

### 개념 보충: 선형 vs 제곱 — 두 개의 벽

컨텍스트를 늘리면 **서로 다른 두 가지 비용**이 동시에 오릅니다. 이걸 구분하는 게 핵심입니다.

```
컨텍스트 S를 2배로 늘리면?

① KV 캐시 메모리:  O(S)   → 2배   (토큰마다 K,V 한 벌씩 저장)
② Prefill Attention 연산: O(S²)  → 4배   (모든 토큰이 모든 토큰을 봄)
③ Decode Attention 연산:  O(S)   → 2배   (새 토큰 1개가 기존 S개를 봄)
```

| 컨텍스트 | KV 캐시 (8B, 배치1) | Prefill 연산 상대량 |
|---|---|---|
| 4,096 | 0.5 GB | 1× |
| 8,192 | 1 GB | 4× |
| 16,384 | 2 GB | 16× |
| 32,768 | 4 GB | 64× |
| 131,072 | 16 GB | 1024× |

**실전 결론:**
- **메모리가 먼저 터진다** → 배치가 클 때 (KV 캐시가 배치 × 컨텍스트)
- **TTFT가 먼저 터진다** → 긴 문서 한 방을 넣을 때 (Prefill이 제곱)
- 그래서 128K 컨텍스트 모델이 "128K를 다 채워 쓸 수 있다"는 뜻은 아닙니다. **VRAM과 인내심의 문제**입니다.

### 개념 보충: "선언된 컨텍스트 ≠ 실제로 기억하는 컨텍스트"

이 단계에서 반드시 체감해야 할 함정입니다.
모델이 32K를 지원한다고 32K 전부를 균등하게 기억하지 않습니다.

- **Lost in the Middle**: 긴 컨텍스트의 **앞과 뒤는 잘 기억하고 중간은 흘립니다.**
- **Needle in a Haystack (NIAH)** 테스트: 긴 텍스트 중간에 특정 문장("바늘")을 심고,
  그걸 찾아내는지 위치·길이별로 격자 테스트를 합니다.
- RoPE scaling으로 컨텍스트를 억지로 늘린 모델은 확장 구간의 품질이 특히 떨어집니다 (→ 15단계).

### 실습

```bash
for len in 4096 8192 16384 32768; do
  vllm serve Qwen/Qwen3-8B --max-model-len $len --gpu-memory-utilization 0.9
  # 로그의 "GPU KV cache size: N tokens" 기록
done
```

측정할 것:
1. `max-model-len`별 **KV 캐시 토큰 수** → 이론 계산과 대조
2. 입력 길이별 **TTFT 곡선** → 로그-로그 그래프로 그리면 기울기 2(제곱)가 보입니다
3. **NIAH 스타일 간단 테스트**: 긴 더미 텍스트 앞/중간/뒤에 "비밀번호는 7391" 을 심고 물어보기

> 💡 컨텍스트가 커서 KV 캐시가 부담이면 `--kv-cache-dtype fp8` 을 시도해보세요.
> KV 캐시가 절반이 되는 대신 품질에 어떤 영향이 있는지 3단계 평가로 재보면 좋은 실습입니다.

### 체크포인트

TTFT vs 입력 길이 그래프를 그려 **제곱 증가를 눈으로 확인**했고,
"32K를 지원한다"와 "32K를 제대로 기억한다"가 다르다는 걸 실측으로 안다.

## 9단계. Parallelism을 돌려봅니다

> ⚠️ **RTX 3090을 2대 가진 분만 가능합니다.** (원문)

### 원문 요지

> - **Tensor Parallel (TP=2) vs Pipeline Parallel (PP=2)** 를 비교해봅니다.
> - 칩이 여러 개 있을 때, 칩들에 **모델 가중치를 나눠서 올린다**거나, 또는 **연산 순서를 여러 칩들에 나눠서 올리는** 테크닉을 익힙니다.

### 개념 보충: 모델을 쪼개는 두 가지 방향

```
[Tensor Parallel] — 각 레이어를 "가로로" 쪼갬
        Layer 1        Layer 2        Layer 3
GPU0:  [왼쪽 절반] ↔ [왼쪽 절반] ↔ [왼쪽 절반]
GPU1:  [오른쪽절반] ↔ [오른쪽절반] ↔ [오른쪽절반]
         ↑ 레이어마다 GPU 간 통신(all-reduce) 필요

[Pipeline Parallel] — 레이어를 "세로로" 쪼갬
GPU0:  [Layer 1-16] ──→
GPU1:              ──→ [Layer 17-32]
         ↑ 경계에서 한 번만 통신 (activation 전달)
```

| | Tensor Parallel (TP) | Pipeline Parallel (PP) |
|---|---|---|
| 쪼개는 대상 | 각 레이어의 가중치 행렬 | 레이어 묶음 |
| GPU 간 통신 | **레이어마다** all-reduce (많음) | 스테이지 경계에서만 (적음) |
| 필요 대역폭 | 높음 (NVLink 권장) | 낮음 (PCIe도 견딤) |
| 단일 요청 지연시간 | **낮음** (GPU를 동시 활용) | 높음 (순차 통과) |
| 유휴 자원 | 적음 | **파이프라인 버블** 발생 |
| 좋은 상황 | 노드 내부, 고속 인터커넥트 | 노드 간, 느린 연결 |

**실전 규칙:**
- 한 대 안에서 NVLink로 묶여 있다 → **TP 우선**
- PCIe만 있거나 여러 노드에 걸쳐 있다 → **PP 고려**
- TP는 보통 GPU 수를 어텐션 헤드 수의 약수로 맞춰야 합니다 (TP=2, 4, 8)

**파이프라인 버블 (PP의 약점):**

```
시간 →
GPU0: [B1][B2][B3][  유휴  ]
GPU1: [  유휴  ][B1][B2][B3]
        ↑ 이 빈 구간이 버블. 마이크로배치를 잘게 쪼개 줄입니다
```

### 실습

```bash
# Tensor Parallel
vllm serve Qwen/Qwen3-14B --tensor-parallel-size 2

# Pipeline Parallel
vllm serve Qwen/Qwen3-14B --pipeline-parallel-size 2
```

관찰 포인트:
1. **VRAM 분배**: `nvidia-smi`로 두 GPU 사용량 확인. TP는 대칭, PP는 비대칭일 수 있음
2. **TTFT/TPOT 비교**: 같은 워크로드로 TP=2 vs PP=2 실측 → **TP가 지연시간에 유리한 걸 확인**
3. **NVLink 효과**: `nvidia-smi nvlink -s` 로 링크 확인. NVLink 유무로 TP 성능이 크게 갈립니다
4. **단독 GPU 대비**: 14B를 1장에 양자화로 올린 것 vs 2장에 TP=2로 BF16으로 올린 것 비교

> 💡 병렬화는 "속도를 위해" 하는 게 아니라 **"안 들어가는 모델을 넣기 위해"** 먼저 합니다.
> 3090 2장 = 48GB가 되면 14B BF16, 32B AWQ 같은 게 실습 범위에 들어옵니다.
> 통신 오버헤드 때문에 GPU 2배가 속도 2배가 되지 않는다는 것도 직접 확인하세요.

### 체크포인트

"모델이 GPU 1장에 안 들어갈 때 TP와 PP 중 무엇을 왜 고르는가"를 자기 실측으로 답할 수 있다.

# Phase 4. 내 모델 만들기

## 10단계. LoRA / QLoRA로 fine-tuning 해봅니다

### 원문 요지

> - 한국어 데이터셋을 받아 **unsloth 또는 axolotl**을 이용해 **SFT 파인튜닝**을 해봅니다.
> - **학습 loss curve, eval loss, overfitting** 등을 직접 봅니다.
> - 이걸 직접 서빙해봄으로써 **'내 모델을 내 하드웨어에서 돌리는 사람'** 으로 거듭납니다.

### 개념 보충 ①: LoRA — 왜 전체를 학습하지 않는가

8B 모델 전체 파인튜닝(Full FT)에 필요한 VRAM:

```
가중치(BF16)        16 GB
그래디언트          16 GB
옵티마이저 상태(Adam) 64 GB   ← momentum + variance, FP32
활성화값             수 GB
─────────────────────────
합계                100 GB+   ← 3090 2장(48GB)으로 불가능
```

LoRA는 **원본 가중치를 얼려두고, 작은 행렬 두 개만 학습**합니다.

```
       원본 가중치 W (d×k, 동결 ❄️)
              +
       B(d×r) × A(r×k)  ← 학습 대상. r=8~64 (rank)

파라미터 수:  d×k  →  r×(d+k)
예: 4096×4096 = 16.7M  →  8×8192 = 65K   (0.4%)
```

- 학습 파라미터가 0.1~1% 수준 → **옵티마이저 상태도 그만큼만** 필요
- 결과물(어댑터)이 수십~수백 MB → 여러 개 만들어 바꿔 끼울 수 있음
- 추론 시 `W + BA`로 합치면(merge) 추가 지연시간 0

### 개념 보충 ②: QLoRA — 여기에 양자화를 더한다

- 원본 가중치를 **4bit(NF4)로 양자화해서 로딩** → 16GB가 4~5GB로
- LoRA 어댑터만 BF16으로 학습
- 핵심 기법: **NF4**(정규분포에 최적화된 4bit), **이중 양자화**(양자화 상수까지 양자화),
  **페이지드 옵티마이저**(메모리 스파이크를 CPU로 넘김)
- 결과: **8B를 24GB 1장에서, 70B를 48GB에서** 학습 가능

> 3단계에서 "양자화는 정확도를 깎는다"고 배웠는데 여기선 양자화를 씁니다. 모순이 아닙니다.
> **얼어있는 원본은 4bit로 눌러도, 학습되는 어댑터가 BF16이면 손실을 상당히 흡수**합니다.

### 개념 보충 ③: 학습 곡선 읽는 법

이 단계의 진짜 학습 목표는 **곡선을 읽는 눈**입니다.

```
정상                    과적합(Overfitting)         학습률 과다
loss                    loss                       loss
 │╲                      │╲                         │╲    ╱╲  ╱
 │ ╲___train             │ ╲___train                │ ╲__╱  ╲╱
 │  ╲___eval             │  ╲    ___eval ↗          │  요동치며 발산
 └──────────→ step       └──────────→ step          └──────────→ step
 둘 다 함께 내려감        eval이 다시 올라감          불안정
```

| 증상 | 해석 | 대응 |
|---|---|---|
| train ↓, eval ↓ | 정상 | 계속 |
| train ↓, eval ↑ | **과적합** | 학습 조기 종료, 데이터 늘리기, rank 낮추기 |
| 둘 다 정체 | 학습률 너무 낮음 / rank 부족 | LR ↑, rank ↑ |
| loss 발산·NaN | 학습률 너무 높음 | LR ↓, warmup 추가, gradient clipping |

**주요 하이퍼파라미터:**

| 파라미터 | 의미 | 실용 시작점 |
|---|---|---|
| `r` (rank) | 어댑터 표현력 | 16 (작으면 8, 크면 64) |
| `lora_alpha` | 어댑터 스케일 | 보통 `r` 또는 `2r` |
| `target_modules` | 어댑터 붙일 레이어 | 전 linear 레이어 권장 |
| `learning_rate` | | 1e-4 ~ 2e-4 |
| `epochs` | | 1~3 (많으면 과적합) |

### 실습

```bash
uv pip install unsloth  # 또는 axolotl
```

한국어 데이터셋 후보: KoAlpaca, ko_wikidata_QA, KOpen-platypus 등 (Hugging Face)

파인튜닝 후 **반드시 세 가지를 하세요:**

1. **정확도 재측정** — 2단계 스크립트로. 특정 태스크는 오르고 일반 능력은 떨어졌을 수 있습니다
   (= **catastrophic forgetting**, 이것도 직접 봐야 하는 현상입니다)
2. **vLLM으로 어댑터 서빙**
   ```bash

   ```

# Phase 5. 시스템 구축 — 모델을 조합해 서비스로

## 11단계. 소형/중형/대형 모델 동시 서빙을 해봅니다

### 원문 요지

> - 1B/3B/8B 모델을 동시에 돌리려면 어떻게 해야 할까요? 간단하게 생각하면 여러 vllm 컨테이너를 돌리면 됩니다.
> - 짧은 컨텍스트의 소형 모델 / 중형 컨텍스트의 중형 모델 / 긴 컨텍스트의 대형 모델
> - 이 3개를 동시에 띄워서 **파이프라이닝**을 해보세요.
> - 마치 **Opus/Sonnet/Haiku 같은 구조**를 만들어봅니다.

### 개념 보충: 모델 라우팅 — 왜 티어를 나누는가

상용 API가 왜 3티어인지 생각해보면 답이 나옵니다. **모든 요청이 최고 성능을 필요로 하지 않습니다.**

```
요청 유입
   ↓
[라우터] ─ 난이도 판정
   ├─ 분류/추출/포맷변환    → 1B  (초고속, 초저비용)
   ├─ 요약/일반 대화         → 3B  (균형)
   └─ 추론/코딩/복잡한 판단  → 8B+ (고품질)
```

| 티어 | 모델 예 | 컨텍스트 | 담당 |
|---|---|---|---|
| 소형 | Qwen3-1.7B | 4K | 라우팅, 분류, 태깅, 키워드 추출 |
| 중형 | Qwen3-4B | 16K | 요약, 재작성, 간단한 QA |
| 대형 | Qwen3-8~14B | 32K+ | 추론, 코드, 최종 답변 생성 |

**VRAM 배분이 이 단계의 실전 과제입니다.** 3개 서버가 같은 GPU를 나눠 쓰려면
`--gpu-memory-utilization`을 각각 조절해야 하고, 합이 1을 넘으면 OOM입니다.

### 실습

```bash
# GPU 1장을 셋이 나눠 쓰는 구성 (합 ≈ 0.9)
CUDA_VISIBLE_DEVICES=0 vllm serve Qwen/Qwen3-1.7B \
  --port 8001 --max-model-len 4096  --gpu-memory-utilization 0.15 &

CUDA_VISIBLE_DEVICES=0 vllm serve Qwen/Qwen3-4B \
  --port 8002 --max-model-len 16384 --gpu-memory-utilization 0.30 &

CUDA_VISIBLE_DEVICES=0 vllm serve Qwen/Qwen3-8B \
  --port 8003 --max-model-len 32768 --gpu-memory-utilization 0.45 &
```

GPU가 2장이면 `CUDA_VISIBLE_DEVICES`로 물리적으로 분리하는 게 훨씬 편합니다.

**파이프라인 예시 — 뉴스 요약:**

```
기사 100건
  → [1B] 관련성 필터링 (100건 → 20건)     ← 대량, 빠르게
  → [4B] 각 기사 요약 (20건)              ← 중간 부하
  → [8B] 20개 요약을 종합해 브리핑 작성   ← 1회, 고품질
```

측정할 것: **"전부 8B로 처리" vs "티어 분리"** 의 총 처리 시간 비교.

> 💡 원문 표현: *"이전에는 GPT-5.5에게 모든 걸 맡겼다면, 이제는 소형/중형/대형 모델에
> 적절히 나눠 넣는 전략을 짜봅니다. 속도가 훨씬 올라감을 체감합니다."* (12단계)

### 체크포인트

3개 모델이 동시에 살아있고, 요청 성격에 따라 다른 모델로 흐르는 파이프라인이 동작한다.
그리고 티어 분리로 전체 처리 시간이 줄어드는 걸 숫자로 보였다.


이 그림을 그려보면 자연스럽게 질문이 생깁니다.
"어느 노드가 병목인가?", "여기서 소형으로 충분한가?", "실패하면 재시도는?"
→ 이 질문들이 13단계 이후의 동기가 됩니다.

## 13단계. RAG 스택 통합

### 원문 요지

> - **BGE-M3 같은 임베딩 모델**과 **Qdrant, Weaviate, Milvus 같은 VectorDB**, **Reranker 모델**까지 해서
> - RAG를 통한 **'장기 기억 메모리'** 를 만들어보세요.
> - 그걸 다시 ML 파이프라인에 엮어보세요.

### 개념 보충: RAG는 왜 "장기 기억"인가

8단계에서 컨텍스트를 "단기 기억"이라고 했습니다. 단기 기억은 두 한계가 있습니다.
- **비싸다**: 컨텍스트 늘리면 KV 캐시 선형 증가, Prefill 제곱 증가
- **휘발된다**: 대화가 끝나면 사라짐

RAG는 지식을 **외부 DB에 두고, 질문마다 필요한 조각만 컨텍스트로 불러옵니다.**

```
                   ┌──────── 장기 기억 (VectorDB) ────────┐
                   │  문서 수만 건의 임베딩 벡터          │
                   └───────────────┬──────────────────────┘
                                   │ ③ 유사 top-k 검색
질문 ──① 임베딩──→ 쿼리 벡터 ──────┘
                                   ↓ ④ 후보 50개
                            [Reranker] ⑤ 정밀 재정렬
                                   ↓ 최종 5개
                          [LLM] ⑥ 컨텍스트에 넣어 답변 생성
```

### 개념 보충: 임베딩과 Reranker는 왜 둘 다 필요한가

이 구분이 RAG 품질의 핵심입니다.

| | 임베딩 (Bi-encoder) | Reranker (Cross-encoder) |
|---|---|---|
| 방식 | 질문·문서를 **따로** 벡터화 후 거리 계산 | 질문+문서를 **함께** 입력해 관련성 점수 산출 |
| 속도 | 매우 빠름 (문서 벡터는 미리 계산) | 느림 (쌍마다 모델 1회 실행) |
| 정확도 | 보통 | 높음 |
| 역할 | 수만 건 → **후보 50건** (재현율 담당) | 50건 → **최종 5건** (정밀도 담당) |

> 비유: 임베딩은 도서관에서 서가를 훑어 관련 있어 보이는 책 50권을 뽑는 것.
> Reranker는 그 50권을 실제로 펼쳐보고 5권을 고르는 것.
> **둘 다 필요합니다.** 전자만 쓰면 엉뚱한 게 섞이고, 후자만 쓰면 수만 건에 못 돌립니다.

**BGE-M3의 특징** (원문이 이걸 지목한 이유):
- **Multi-Lingual**: 100여 개 언어 — **한국어 성능이 좋습니다**
- **Multi-Granularity**: 최대 8192 토큰까지 긴 문서 임베딩
- **Multi-Functionality**: 한 모델로 밀집(dense) + 희소(sparse/lexical) + 멀티벡터 검색 동시 지원
  → **하이브리드 검색**(의미 검색 + 키워드 검색)을 모델 하나로 구현 가능

### 개념 보충: VectorDB 선택과 청킹

| DB | 특징 |
|---|---|
| **Qdrant** | Rust 기반, 가볍고 빠름. 단일 노드 로컬 실습에 가장 적합 |
| **Milvus** | 대규모·분산에 강함. 구성 요소가 많아 무거움 |
| **Weaviate** | 하이브리드 검색·모듈 생태계가 강점 |
| **pgvector** | 이미 PostgreSQL을 쓰고 있다면 최소 비용 선택 |

> 💡 **RAG 품질의 절반 이상은 청킹(chunking)에서 결정됩니다.** 모델이 아닙니다.
> - 문단/제목 경계를 존중해 자를 것 (문장 중간에서 자르면 의미가 깨짐)
> - 청크 간 겹침(overlap) 10~20% 정도를 둘 것
> - 표·코드 블록은 쪼개지 말 것
> - 청크에 출처 메타데이터(문서명, 섹션)를 붙여 인용 가능하게 할 것

### 실습

```bash
# Qdrant
docker run -p 6333:6333 -v qdrant_storage:/qdrant/storage qdrant/qdrant

# 임베딩 · Reranker도 vLLM으로 서빙할 수 있습니다
vllm serve BAAI/bge-m3 --task embed --port 8010
vllm serve BAAI/bge-reranker-v2-m3 --task score --port 8011
```

**반드시 RAG 평가를 하세요.** 안 하면 "그럭저럭 되는 것 같다"에서 멈춥니다.

| 지표 | 재는 것 |
|---|---|
| Recall@k / MRR | 검색이 정답 문서를 가져왔는가 |
| Faithfulness | 답변이 가져온 문서에 근거하는가 (환각 여부) |
| Answer Relevancy | 답변이 질문에 맞는가 |

- Reranker **on/off** 로 답변 품질을 A/B 비교 → Reranker의 가치를 숫자로 확인
- 12단계 파이프라인에 붙여 "장기 기억을 가진 자동화"로 완성

### 체크포인트

내 문서를 넣으면 근거와 함께 답하는 RAG가 동작하고,
Reranker 유무·청킹 전략 변경의 효과를 평가 지표로 비교할 수 있다.

## 14단계. llama.cpp 소스를 뜯어보며 커널을 확인합니다

### 원문 요지

> - 동일 연산에 **다양한 커널이 있음**을 확인합니다.
> - 똑같은 결과를 내뱉는 conv, GEMM, attention 연산임에도, **속도, 전력, 메모리 목적에 따라 다른 구현**이 있음을 확인합니다.
> - 커널을 파면서 **양자화 precision마다 연산 알고리즘이 다른 것**도 확인합니다 (e.g. FP16, BF16, FP8, INT8, INT4, mixed precision GEMM)
> - **커널을 바꿔가며 성능 변화를 체감합니다.**

### 개념 보충: 커널이란 무엇인가

**커널(kernel) = GPU에서 실행되는 하나의 함수.** 수천 개 스레드가 동시에 이 함수를 실행합니다.

`C = A @ B` 라는 한 줄이 GPU에서는 수십 가지로 구현될 수 있습니다.

```
같은 GEMM(행렬곱)의 여러 구현:
├─ 타일 크기: 128×128? 64×256?           (SM 점유율 vs 레지스터 압박)
├─ 메모리 계층 활용: shared memory 스테이징 방식
├─ 명령어: FMA? Tensor Core (mma/wgmma)?
├─ 정밀도: FP16 누산? FP32 누산?          (속도 vs 수치 안정성)
└─ 대상 아키텍처: Ampere(3090)? Hopper? Blackwell?
```

**결과는 같지만 성능은 수 배에서 수십 배까지 차이 납니다.**
그래서 라이브러리는 상황별로 여러 구현을 두고 런타임에 고릅니다 (이게 **커널 디스패치**).

`llama.cpp`가 학습 자료로 좋은 이유:
- 의존성이 적어 **커널부터 스케줄링까지 한 저장소에서 다 읽힙니다**
- 같은 연산의 CPU(AVX/NEON) / CUDA / Metal / Vulkan 구현을 **나란히 비교**할 수 있습니다
- 양자화 포맷별 커널이 명시적으로 분리되어 있습니다

### 개념 보충: 왜 양자화마다 알고리즘이 다른가

이게 이 단계의 핵심 통찰입니다. **4bit 가중치를 4bit로 곱하는 게 아닙니다.**

```
Q4_K 행렬곱의 실제 흐름:
1. VRAM에서 4bit 패킹된 가중치를 읽음        ← 대역폭 절약 (여기가 이득)
2. 블록별 스케일/최소값을 함께 읽음
3. 레지스터에서 역양자화 (dequantize) → FP16
4. FP16으로 곱셈, FP32로 누산
```

즉 **연산 자체는 여전히 부동소수점**이고, 이득은 **"VRAM에서 읽는 바이트 수"** 에서 나옵니다.
5단계에서 배운 "Decode는 메모리 대역폭 병목"과 정확히 맞물립니다.

| 정밀도 | 특징 |
|---|---|
| FP16 / BF16 | 표준. BF16은 지수부가 넓어 학습에서 안정적 |
| FP8 (E4M3/E5M2) | **Ada(4090) / Hopper 이후** Tensor Core 네이티브. 3090(Ampere)에서는 가속 없음 |
| FP4 (NVFP4 등) | **Blackwell(5090)부터** Tensor Core 네이티브. 그 이전 세대에서는 가속 없음 |
| INT8 | 스케일 기반 정수 연산. **Turing 이후** Tensor Core 가속 있음 |
| INT4 | 대역폭 최소. 역양자화 오버헤드 존재 |
| Mixed Precision | 가중치 INT4 × 활성화 FP16 (**W4A16**) 같은 조합 |

> 📌 **세대별 Tensor Core 정밀도 지원** — "최신 포맷이 내 GPU에서 빠른가"를 판단하는 기준입니다.
>
> | 아키텍처 | 대표 GPU | 새로 추가된 정밀도 |
> |---|---|---|
> | Turing (sm_75) | RTX 2080 Ti | FP16, INT8, INT4 |
> | Ampere (sm_86) | **RTX 3090** | + BF16, TF32 |
> | Ada Lovelace (sm_89) | RTX 4090 | + **FP8** |
> | Hopper (sm_90) | H100 | + FP8 (대폭 강화), wgmma / TMA |
> | Blackwell (sm_120) | **RTX 5090** | + **FP4 / FP6** |

> 💡 3090은 Ampere입니다. FP8/FP4 하드웨어 가속이 없습니다.
> "NVFP4가 빠르다더라"가 내 GPU에서는 안 통하는 이유를 여기서 이해하게 됩니다.
> **"최신 기법"이 아니라 "내 하드웨어에 맞는 기법"이 빠릅니다.**

```bash
cmake -B build -DGGML_CUDA=ON && cmake --build build -j
```

- `ggml/src/ggml-cpu/` — 같은 연산의 CPU/SIMD 구현
- 커널 선택 로직: `ggml_cuda_mul_mat` 안의 분기 조건들을 따라가보세요

같은 연산에 대해 커널/빌드 옵션을 바꿔 **성능 차이를 실측**했고,
왜 그런 차이가 나는지(대역폭? Tensor Core? 역양자화 비용?) 가설을 세울 수 있다.

## 15단계. 다양한 연산 알고리즘의 종류를 이해합니다

### 원문 요지

> - **Attention 기법들**: Flash attention (v1, v2, v3), Paged attention, Radix attention
> - **Long context 기법**: RoPE scaling, YaRN, Sliding window attention, TurboQuant
> - **Speculative decoding**
> - **Prefill/Decode disaggregation**
>
> 위 내용을 이해하면 좋습니다.
> **알고리즘과 코드까지 다 이해할 필요는 없습니다 (거기는 대학원생의 영역).**
> GPT와의 대화를 통해 **'이런 것이 있구나~' 정도만 익혀도 충분합니다.**
> 어차피 나중에 내가 직접 구현 안 하고 LLM이 구현해줍니다.

> 📌 이 단계의 태도가 중요합니다. **깊이 파는 단계가 아니라 지도를 그리는 단계입니다.**
> 각 기법의 "무엇을 해결하려고 나왔는가"만 잡으면 됩니다.

### Attention 계열

| 기법 | 해결하려는 문제 | 핵심 아이디어 |
|---|---|---|
| **Flash Attention** | S×S attention 행렬을 HBM에 쓰는 게 병목 | 타일 단위로 SRAM에서 처리하고 **행렬을 아예 만들지 않음**(online softmax). 메모리 O(S²)→O(S) |
| **FA v2** | v1의 병렬화가 부족 | 시퀀스 길이 방향 병렬화, non-matmul 연산 축소 |
| **FA v3** | Hopper의 새 하드웨어 미활용 | wgmma, TMA, FP8 활용. **Hopper 전용 — 3090에서는 v2까지** |
| **PagedAttention** | KV 캐시 단편화 (→7단계) | 블록 단위 페이징 + 블록 공유 |
| **Radix Attention** | 프리픽스 캐시를 요청별로만 쓰는 낭비 | **radix tree**로 여러 요청의 공통 프리픽스를 트리로 공유 (SGLang) |

> 💡 Flash Attention은 "attention을 근사하는" 게 아닙니다. **결과가 정확히 같습니다(exact).**
> 바뀐 건 계산 순서와 메모리 접근 패턴뿐입니다. 이게 왜 중요한지 이해하면
> "IO-awareness"라는 성능 엔지니어링의 핵심 개념을 얻은 것입니다.

### Long Context 계열

| 기법 | 아이디어 |
|---|---|
| **RoPE scaling** | 위치 인코딩 주파수를 늘려 학습 길이보다 긴 컨텍스트를 다루게 함. 단순 보간은 품질 손실 큼 |
| **YaRN** | 주파수 대역별로 다르게 보간(NTK-aware) + 어텐션 온도 보정. 적은 추가 학습으로 컨텍스트 확장 |
| **Sliding Window Attention** | 각 토큰이 최근 W개만 봄 → 연산 O(S²)→O(S·W), KV 캐시도 상한 고정 |
| **TurboQuant** | KV 캐시 양자화 계열 기법. 긴 컨텍스트에서 캐시 메모리를 줄이는 방향 |

### Speculative Decoding — Decode 병목을 우회하는 트릭

```
[기존]     8B 모델이 한 토큰씩 → 매번 16GB 읽기
[Spec Dec]
  ① 작은 draft 모델(1B)이 앞으로 5토큰을 빠르게 추측
  ② 큰 모델(8B)이 그 5토큰을 "한 번에" 검증 (= prefill처럼 병렬!)
  ③ 맞은 것까지 채택, 틀린 지점부터 다시
  → 큰 모델 실행 1회에 여러 토큰 확정
```

핵심: **출력 분포가 원본과 동일하게 보장**됩니다(rejection sampling). 품질 손실 없이 속도만 얻습니다.
Decode가 메모리 대역폭 병목이라 "연산 여유는 남아있다"는 사실을 이용한 것입니다.
변형: **Medusa**(추가 헤드), **EAGLE**(피처 수준 예측), **n-gram/lookahead**(모델 없이 반복 패턴 활용).

### Prefill/Decode Disaggregation

5단계에서 배운 "Prefill은 compute-bound, Decode는 memory-bound"를 극단적으로 활용합니다.

```
[결합형]  한 GPU가 prefill과 decode를 섞어 처리
          → prefill이 끼어들 때 decode 중인 사용자의 TPOT이 튐 (interference)

[분리형]  GPU A: prefill 전담 → KV 캐시를 GPU B로 전송 → GPU B: decode 전담
          → 서로 방해하지 않음. TTFT와 TPOT을 독립적으로 튜닝 가능
```

각 단계에 다른 병렬화 전략·다른 하드웨어를 붙일 수 있다는 게 큰 장점입니다.

- LLM에게 설명을 받은 뒤, **"방금 설명에서 틀린 부분이 있는지 검토해줘"** 를 한 번 더 던지세요
  (관련 스레드 댓글의 팁 — 검증 단계를 넣으면 정확도가 확실히 올라갑니다)
- vLLM에서 실제로 켜서 체감해볼 수 있는 것들:


## 16단계. 레이어 별 양자화를 해봅니다

### 원문 요지

> - **GPTQ, AWQ, SmoothQuant** 등 모델 가중치를 로딩 후, **레이어마다 양자화**를 해봅니다.
> - 이전의 ollama는 전체 모델을 양자화했다면, 우리는 레이어마다 양자화를 해봅니다.
> - **Profiling 툴**을 익혀서 속도를 측정하고, MMLU Pro + HumanEval을 통해 정확도를 측정합니다.
> - **임베딩 레이어는 양자화를 하면 성능이 급격하게 떨어지고, 뒤에 decode 레이어는 영향을 덜 받는 것**도 확인합니다.

### 개념 보충: 균일 양자화 vs 보정 기반 양자화

3단계의 GGUF 양자화는 **모델만 보고** 숫자를 눌렀습니다(data-free).
이 단계의 기법들은 **데이터를 흘려보내며** 어디가 민감한지 측정하고 그에 맞춰 누릅니다(calibration).

| 기법 | 접근 | 특징 |
|---|---|---|
| **GPTQ** | 레이어별 2차 정보(Hessian)로 오차를 최소화하며 순차 양자화 | 4bit에서 품질 유지 우수. 양자화 시간이 김 |
| **AWQ** | **활성화 크기**를 보고 중요한 채널(1% 미만)을 보호(스케일 조정) | 빠르고 일반화 잘 됨. W4A16 추론에 널리 쓰임 |
| **SmoothQuant** | 활성화의 이상치를 가중치로 "옮겨" 양자화 난이도를 균등화 | **W8A8**(활성화까지 8bit) 실현. 연산 자체를 INT8로 |

**AWQ의 직관 (가장 이해하기 쉬움):**
```
가중치 채널 중 극소수(<1%)가 출력에 압도적 영향을 미칩니다.
→ 그 채널만 스케일을 키워 양자화 오차의 상대적 영향을 줄임
→ 나머지는 과감하게 4bit로

"모든 가중치가 동등하지 않다(weights are not equally important)"
```

### 개념 보충: 왜 레이어마다 민감도가 다른가

원문이 지목한 현상이 이 단계의 핵심 관찰입니다.

```
[임베딩 / lm_head]     양자화 민감 ●●●●●  ← 여기 뭉개면 토큰 표현 자체가 붕괴
[초반 트랜스포머 블록] 민감      ●●●●     ← 저수준 특징, 이후 전 레이어에 전파
[중간 블록]            둔감      ●●       ← 여유(redundancy)가 큼
[후반 블록]            둔감      ●●
[특정 어텐션 투영]     민감      ●●●●     ← 이상치 채널이 몰려 있는 경우
```

이유: 임베딩/출력 레이어는 **어휘 전체와 직결된 병목**이고,
초반 레이어의 오차는 뒤로 **누적 전파**됩니다.
반면 중간 블록은 residual 연결 덕에 개별 레이어의 오차 여유가 큽니다.

**실전 결론: 균일하게 4bit로 누르는 건 낭비이자 손해입니다.**
민감한 곳은 8bit/16bit로 남기고, 둔감한 곳은 4bit 이하로. 이게 **mixed-precision 양자화**입니다.

## 17단계. 커스텀 Triton Kernel을 짜봅니다

### 원문 요지

> - **Kernel fusion**이라는 개념을 익혀야 합니다.
> - 커널은 호출할 때마다 **메모리에 접근하고 연산하는 오버헤드**가 생깁니다.
> - 따라서 아래와 같은 형태는 4번의 오버헤드가 생깁니다.
>   `[매트릭스 연산 1] → [벡터 연산 1] → [매트릭스 연산 2] → [벡터 연산 2]`
> - 커널 퓨전을 통해, 메모리에 접근하는 횟수를 최소화할 수 있습니다.
>   `[매트릭스 연산 1 + 벡터 연산 1 + 매트릭스 연산 2 + 벡터 연산 2]`
> - 이 개념을 가지고, 간단한 커널을 짜봅니다. **RMSNorm + RoPE** 같은 걸 짜보고, 성능이 얼마나 올라가는지 봅니다.
> - **Kernel fusion만 잘 해도 속도가 엄청나게 올라가는 걸 확인합니다.**
> - **이거이거, 밥 벌어먹고 살 만한 기술을 익힌 것 같습니다.**

### 개념 보충: 왜 퓨전이 그렇게 효과적인가

GPU의 진짜 병목은 연산이 아니라 **메모리 왕복**입니다.

```
RTX 3090 기준 대략적인 비율:
  연산 성능:      ~35 TFLOPS (FP32) / ~142 TFLOPS (FP16 Tensor Core)
  메모리 대역폭:  ~936 GB/s

→ 데이터 1바이트를 읽어오는 시간에 수십~수백 번의 연산을 할 수 있습니다.
→ 즉 "읽고 쓰는 횟수"가 성능을 지배합니다.
```

```
[퓨전 없음]  커널마다 HBM(VRAM) 왕복
 HBM ─읽기→ [커널1] ─쓰기→ HBM ─읽기→ [커널2] ─쓰기→ HBM ...
        ↑ 이 왕복이 실제 계산보다 오래 걸림

[퓨전]  한 커널 안에서 레지스터/SRAM에 데이터를 붙잡고 연속 처리
 HBM ─읽기→ [커널1+2+3+4] ─쓰기→ HBM
```

**핵심 개념 — 산술 강도 (Arithmetic Intensity):**
```
산술 강도 = 연산 횟수 / 메모리 전송 바이트

낮음 (memory-bound)  : elementwise 연산, LayerNorm, softmax, decode 단계 GEMV
높음 (compute-bound) : 큰 행렬곱, prefill 단계 GEMM
```
**퓨전은 memory-bound 연산들을 묶어 산술 강도를 끌어올리는 기법입니다.**
LayerNorm/RMSNorm/RoPE/활성화 함수 같은 것들이 퓨전의 1급 후보인 이유입니다.
Flash Attention(15단계)도 결국 **attention 전체를 퓨전한 것**입니다.

### 개념 보충: Triton이란

CUDA C++보다 훨씬 낮은 진입 장벽으로 GPU 커널을 쓰게 해주는 파이썬 DSL입니다.

| | CUDA C++ | Triton |
|---|---|---|
| 사고 단위 | 스레드 하나 | **블록(타일) 하나** |
| shared memory | 직접 관리 | **컴파일러가 처리** |
| 메모리 coalescing | 직접 신경 | 대체로 자동 |
| 언어 | C++ | Python |

즉 "블록 단위로 데이터를 가져와서 처리한다"는 수준으로 생각하면 되고,
저수준 최적화는 컴파일러가 상당 부분 해줍니다. vLLM·PyTorch 내부에도 Triton 커널이 많습니다.

### 실습 — 단계적으로 올리기

**1) 워밍업: elementwise 퓨전**
```python
import torch, triton, triton.language as tl

@triton.jit
def add_relu_kernel(x_ptr, y_ptr, out_ptr, n, BLOCK: tl.constexpr):
    pid = tl.program_id(0)
    offs = pid * BLOCK + tl.arange(0, BLOCK)
    mask = offs < n
    x = tl.load(x_ptr + offs, mask=mask)
    y = tl.load(y_ptr + offs, mask=mask)
    tl.store(out_ptr + offs, tl.maximum(x + y, 0.0), mask=mask)   # ← 두 연산을 한 번에
```
비교 대상: `torch.relu(x + y)` (커널 2개 = HBM 왕복 2회)

**2) 본 과제: RMSNorm + RoPE 퓨전** (원문 지정)
```
비퓨전:  RMSNorm 커널 (읽기/쓰기) → RoPE 커널 (읽기/쓰기)   = HBM 왕복 2회
퓨전:    한 커널에서 정규화 후 곧바로 회전 적용             = HBM 왕복 1회
```
RMSNorm과 RoPE는 둘 다 memory-bound이므로 **거의 2배에 가까운 개선**을 볼 수 있습니다.

**3) 검증과 측정 — 반드시 할 것**
```python
# 정확성 먼저
torch.testing.assert_close(triton_out, torch_ref, rtol=1e-3, atol=1e-3)

# 그 다음 성능
print(triton.testing.do_bench(lambda: fused(x)))
print(triton.testing.do_bench(lambda: torch_ref_impl(x)))
```

> ⚠️ **빠르지만 틀린 커널은 아무 가치가 없습니다.** 항상 참조 구현과 수치 비교부터.

**4) 심화**
- `triton.autotune`으로 `BLOCK_SIZE`, `num_warps` 자동 탐색
- `ncu`로 **달성 대역폭 / 이론 대역폭** 비율 확인 → 80% 넘으면 잘 만든 것
- 원본 PyTorch 구현 대비 개선폭을 표로 정리

# Phase 7. 심화 — 생태계 전체를 조망한다

## 18단계. MoE 계열 코드를 뜯어봅니다

### 원문 요지

> - **Mixtral, Qwen3-MoE, DeepSeek** 계열 코드를 뜯어봅니다.
> - **Expert routing, all-to-all 통신, Expert Parallel (EP)** 가 **완전히 다른 개념**임을 익힙니다.

### 개념 보충: MoE — "전부 다 쓰지 않는" 모델

```
[Dense 모델]  모든 토큰이 모든 파라미터를 통과
              8B 모델 → 매 토큰 8B 전부 연산

[MoE 모델]    FFN 자리에 전문가(expert) N개, 토큰마다 top-k개만 활성
              총 파라미터 47B, 활성 파라미터 13B  (Mixtral 8x7B)
              → 47B의 지식 용량, 13B의 연산 비용
```

**중요한 함정: 메모리는 총 파라미터, 연산은 활성 파라미터를 따릅니다.**
Mixtral 8x7B는 13B만 연산하지만 **47B 전부를 VRAM에 올려야** 합니다.
로컬 환경에서 MoE가 어려운 이유가 이것입니다.

### 원문이 강조한 세 개념의 구분

원문이 "완전히 다른 개념"이라고 못 박은 이유가 있습니다. 자주 뭉개져 이해됩니다.

**① Expert Routing — 알고리즘 (모델 구조)**
```
토큰 → [Gating Network] → 점수 [0.6, 0.1, 0.2, ...] → top-2 전문가 선택
```
- 학습 단계의 관심사: 부하 불균형(특정 전문가에 쏠림)을 막는 **auxiliary loss**,
  **capacity factor**(전문가당 처리 상한), 토큰 드롭
- DeepSeek 계열은 **fine-grained expert**(전문가를 잘게 쪼갬) + **shared expert**(항상 활성) 같은 변형을 씀

**② All-to-All 통신 — 통신 패턴 (구현 수단)**
```
전문가가 여러 GPU에 흩어져 있으면:
  각 GPU의 토큰들 → 각자 배정된 전문가가 있는 GPU로 보내야 함 (dispatch)
  전문가 처리 후 → 원래 GPU로 돌려받아야 함 (combine)
  → 모든 GPU가 모든 GPU와 통신 = all-to-all
```
- MoE 추론 지연시간의 **상당 부분이 이 통신**입니다. all-reduce(TP)와는 다른 패턴입니다
- 이게 MoE 서빙의 최대 난관이고, 전용 커널(DeepEP 등)이 나오는 이유입니다

**③ Expert Parallel (EP) — 병렬화 전략 (배치 방식)**
```
TP: 각 레이어의 가중치를 GPU들이 쪼개 가짐
EP: 전문가 단위로 GPU에 배분 (GPU0: expert 0-3, GPU1: expert 4-7)
```
- 9단계의 TP/PP와 나란히 놓고 보면 이해가 쉽습니다: **"무엇을 기준으로 쪼개는가"의 차이**
- EP는 전문가 부하 불균형 시 특정 GPU만 바빠지는 문제가 있어 **expert 재배치/복제**가 필요합니다

> 💡 세 개념의 관계: **routing(무엇을 고를지) → all-to-all(어떻게 보낼지) → EP(어디에 둘지)**
> 서로 다른 층위의 결정입니다.

### 실습

```bash

vllm serve Qwen/Qwen3-30B-A3B-Instruct-2507-FP8 --tensor-parallel-size 2
```

관찰 포인트:

## 19단계. VLM / 멀티모달 모델 서빙을 해봅니다

### 원문 요지

> **Vision encoder와 LLM의 prefill 비대칭, 이미지 토큰화, Dynamic resolution** 등 테크닉을 익힙니다.

### 개념 보충: VLM의 구조

```
이미지 ─→ [Vision Encoder] ─→ [Projector] ─→ 이미지 토큰 ─┐
          (ViT/SigLIP)        (MLP 등)                     ├→ [LLM] → 답변
텍스트 ────────────────────→ 텍스트 토큰 ─────────────────┘
```

### 원문이 지목한 세 가지 테크닉

**① Prefill 비대칭 — VLM 서빙의 최대 난제**

```
텍스트 요청:  "이 코드 리뷰해줘"                  →  10 토큰
이미지 요청:  1024×1024 이미지 1장                → 수백~수천 토큰
```

여기서 문제가 겹칩니다.
- **TTFT 급증**: 이미지 토큰 수가 많고, Prefill은 제곱으로 늘어남 (8단계)
- **파이프라인 불균형**: Vision Encoder(작고 compute-bound)와 LLM(크고 memory-bound)이
  서로 다른 성격 → 하나가 노는 동안 다른 하나가 바쁨
- **배치 예측 불가**: 요청마다 이미지 토큰 수가 달라 KV 캐시 예약이 어려움
- **캐싱 어려움**: 텍스트 프리픽스 캐싱은 쉽지만 이미지는 재사용률이 낮음

→ 실전 대응: vision encoder를 별도 프로세스/GPU로 분리, 이미지 임베딩 캐싱,
이미지 요청과 텍스트 요청의 스케줄링 분리.

**② 이미지 토큰화 — 이미지가 몇 토큰이 되는가**

```
1024×1024 이미지, 패치 14×14
  → (1024/14)² ≈ 5,300 패치
  → Pixel Unshuffle / Pooling 등으로 압축 → 수백~수천 토큰
```
"이미지 한 장 = 텍스트 몇 페이지" 라는 감각을 가지는 게 중요합니다.
컨텍스트 예산 계산에 직접 들어갑니다.

**③ Dynamic Resolution — 고정 크기 리사이즈의 한계 극복**

```
[고정 해상도]  모든 이미지를 336×336으로 → 긴 문서 스캔은 글자가 뭉개짐
[Dynamic Res]  종횡비 유지하며 필요한 만큼의 패치 사용 (Qwen2-VL의 Naive Dynamic Resolution)
               → 작은 이미지는 적은 토큰, 큰 이미지는 많은 토큰
               → 품질 ↑, 하지만 토큰 수가 가변 = 서빙이 더 어려워짐
```
관련: **AnyRes / 타일링**(이미지를 격자로 쪼개 각각 인코딩 + 전체 축소본),
**M-RoPE**(시간·높이·너비 축으로 위치 인코딩 분해).

### 실습

```bash
vllm serve Qwen/Qwen2.5-VL-7B-Instruct \
  --max-model-len 16384 \
  --limit-mm-per-prompt '{"image": 2}' \
  --mm-processor-kwargs '{"min_pixels": 200704, "max_pixels": 1003520}'
```

측정할 것:
1. **이미지 해상도별 TTFT** — `max_pixels`를 바꿔가며. 토큰 수와 TTFT의 관계 확인
2. **텍스트 전용 요청 vs 이미지 요청**의 TTFT 차이 (비대칭 체감)
3. **혼합 워크로드**: 이미지 요청이 섞였을 때 텍스트 사용자의 TPOT이 어떻게 튀는지
4. 실용 과제: 문서 스캔 이미지 → 표 추출 파이프라인 (12·13단계와 연결)

```
  vLLM 프리픽스 캐싱: 요청 단위로 블록 재사용
  SGLang RadixAttention: 여러 요청·분기의 공통 프리픽스를 트리로 공유
  → 분기가 많은 에이전트 트리에서 SGLang이 유리할 수 있습니다
```

**엔진 선택은 워크로드 특성의 함수입니다.**

| 배치 문서 처리 | 최대 처리량 | 큰 배치, TensorRT-LLM |
| 에이전트/멀티턴 | 프리픽스 재사용 | SGLang |
| 단일 사용자 로컬 | 편의성, 저VRAM | llama.cpp |

## 21단계. NVIDIA GPU가 아닌 다른 NPU도 기웃거려봅니다

### 원문 요지

> - 반도체의 전설 **짐 켈러**와 비전을 함께 맞춰볼 생각이 점점 듭니다.
> - **(후후 여긴 농담)**

> 📌 원문 저자가 "농담"이라고 밝혔듯 이 단계는 반쯤 홍보성 서술입니다.
> 언급된 회사는 **Tenstorrent**(CEO 짐 켈러, 1단계의 Blackhole 카드)입니다.
> 다만 "NVIDIA 밖의 스택을 봐야 이해가 완성된다"는 취지 자체는 유효합니다.

### 개념 보충: 왜 다른 하드웨어를 봐야 하는가

**CUDA만 쓰면 "무엇이 GPU의 본질이고 무엇이 CUDA의 관습인지" 구분이 안 됩니다.**

다른 스택을 보면 이런 것들이 분리되어 보입니다.

| 질문 | CUDA만 볼 때 | 다른 스택을 볼 때 |
|---|---|---|
| SIMT 스레드 모델은 필수인가? | 당연해 보임 | 데이터플로/systolic 등 다른 모델 존재 |
| HBM ↔ SRAM 계층은 필수인가? | 당연해 보임 | 대용량 온칩 SRAM 아키텍처 존재 |
| 커널을 손으로 짜야 하는가? | 당연해 보임 | 컴파일러가 그래프 단위로 스케줄링 |

**주요 대안 스택:**

| 플랫폼 | 소프트웨어 | 특징 |
|---|---|---|
| **AMD** (MI300X 등) | ROCm + HIP | CUDA와 유사한 프로그래밍 모델. vLLM 지원 있음. 대용량 HBM |
| **Tenstorrent** (Blackhole) | TT-Metalium / TT-NN / tt-forge | **전 스택 오픈소스**. 데이터플로 아키텍처, Ethernet 기반 확장 |
| **Intel** (Gaudi, Arc) | SynapseAI / oneAPI | |
| **Google** (TPU) | XLA / JAX | 컴파일러 중심. 개인 구매 불가(클라우드) |
| 컴파일러 계층 | **MLIR**, TVM, IREE | 하드웨어 중립 중간 표현. 이쪽을 알면 이식성이 생김 |

> 💡 **오픈소스 스택의 학습 가치**가 이 단계의 실질적 포인트입니다.
> CUDA 커널은 PTX/SASS 아래로 내려가면 문서화되지 않은 영역이 나옵니다.
> 컴파일러부터 펌웨어까지 다 열려 있으면 **"내 행렬곱이 실제로 어떤 명령으로 바뀌는지" 끝까지 추적**할 수 있습니다.
> 이건 성능 엔지니어링을 배우는 사람에게 확실한 장점입니다.

### 실습 (하드웨어 없이도 가능한 것들)

- 대안 스택의 **오픈소스 저장소를 읽어보기** — 커널 표현 방식이 CUDA와 어떻게 다른지
- `torch.compile` / **MLIR** 계층을 만져보며 "컴파일러가 퓨전을 자동으로 하는" 세계 체험
  ```python
  model = torch.compile(model)   # 17단계에서 손으로 한 퓨전을 컴파일러가 시도
  ```
  → 17단계에서 직접 짠 퓨전 커널과 컴파일러 결과를 비교하면 배우는 게 많습니다
- ROCm/기타 백엔드에서 vLLM이 어떻게 추상화되어 있는지 (`vllm/platforms/`) 확인
- 클라우드로 AMD/TPU 인스턴스를 짧게 빌려 같은 벤치마크를 돌려보기

### 체크포인트

"이 최적화 기법은 하드웨어 본질에서 오는 것"과
"이건 NVIDIA 스택의 특수성"을 구분해서 말할 수 있다.

### 원문의 맺음말

> 여기까지 Local AI를 다루고 싶은 분들을 위한 가이드였습니다.
> **하루아침만에 공부할 수 있는 내용은 아니기에, 저장하시고 종종 보시면서 공부하시면 좋겠습니다.**

### 이 커리큘럼을 끝내면 얻는 것

```
1~3단계    →  "정확도는 공짜가 아니다"를 측정으로 안다
4~6단계    →  Prefill/Decode를 나눠 생각한다. 성능을 숫자로 말한다
7~9단계    →  메모리와 처리량의 트레이드오프를 계산으로 예측한다
10단계     →  학습부터 서빙까지 한 사이클을 자기 손으로 돌렸다
11~13단계  →  모델을 조합해 실제로 쓰이는 시스템을 만든다
14~17단계  →  성능이 왜 그런지 알고, 커널 수준에서 고칠 수 있다
18~21단계  →  생태계 전체의 지도를 갖는다
```

### 학습 원칙 정리

1. **측정 먼저.** 2단계에서 평가 도구를 손에 쥐는 이유. 못 재면 최적화도 없습니다.
2. **체감 우선.** 논문을 읽어서 아는 것과 메모리가 터지는 걸 보고 아는 것은 다릅니다.
3. **기록하라.** 각 단계의 표를 실제로 채우세요. 이게 나중에 포트폴리오가 됩니다.
4. **LLM을 조교로 쓰되 검증하라.**
   > 관련 팁: 설명을 받은 뒤 **"방금 설명한 내용에서 틀린 부분이 있는지 검토해줘"** 를 한 번 더 던지면
   > 정확도가 눈에 띄게 올라갑니다.
5. **막히면 앞 단계로.** 7단계가 안 풀리면 5단계의 Prefill/Decode 이해가 부족한 것입니다.

# 부록 A. 로컬 코딩 에이전트 붙이기

> Claude Code처럼 터미널에서 쓰는 코딩 에이전트를 **내 로컬 모델**에 연결하는 방법입니다.
> 커리큘럼 4~8단계(vLLM 서빙, 컨텍스트, KV 캐시)를 배운 뒤 읽으면 전부 실전 문제로 연결됩니다.

## A-1. 층위 정리 — 세 종류의 도구는 서로 다른 계층입니다

이름이 비슷해 보이는 도구들이 실은 다른 층위에 있습니다. 이걸 구분하는 게 먼저입니다.

```
┌─ OpenClaw ────────────────────────────────────────────────┐
│  개인 비서 에이전트 — 코딩 도구가 아님                     │
│  메신저로 지시 → 이메일/캘린더/브라우저/파일 조작          │
│  상시 백그라운드 실행 (heartbeat)                          │
└───────────────────────────────────────────────────────────┘
        ※ 아래 두 개와 계보가 완전히 다름

┌─ Orca ────────────────────────────────────────────────────┐
│  오케스트레이터 (ADE) — 에이전트를 "여러 개 돌리는" 껍데기  │
│  각 작업을 git worktree로 격리, 40+ CLI 에이전트 래핑       │
└──────────────────┬────────────────────────────────────────┘
                   │ 이 안에서 실행되는 것들 ↓
┌─ opencode / aider / crush / goose ────────────────────────┐
│  코딩 에이전트 본체 — Claude Code의 대체재                 │
│  터미널 TUI, 파일 읽기/편집, 셸 실행                       │
└──────────────────┬────────────────────────────────────────┘
                   │ 모델을 갈아끼우는 자리 ↓
┌─ vLLM / Ollama (로컬 모델) 또는 클라우드 API ─────────────┐
└───────────────────────────────────────────────────────────┘
```

**Orca는 opencode의 경쟁자가 아니라 상위 래퍼**이고, **OpenClaw는 아예 다른 카테고리**입니다.

## A-2. 터미널 코딩 에이전트 선택

| 툴 | 성격 | 로컬 모델 | 특징 |
|---|---|---|---|
| **opencode** | 범용 TUI 에이전트 | Ollama + OpenAI 호환 75+ 프로바이더 | 이 분야 최다 스타(~165k). Claude Code와 사용 경험이 가장 비슷 |
| **aider** | Git 중심 편집기 | 모든 OpenAI 호환 API | 커밋 단위 작업. 다중 파일 편집이 정교함. 자율성 낮고 통제력 높음 |
| **crush** | TUI 에이전트 (Charm) | 지원 | 터미널 UI 완성도 높음. FSL 라이선스(2년 후 MIT 전환) |
| **goose** | 코딩 + 범용 자동화 | Ollama 네이티브 | 2026년 4월 Linux Foundation 기부 → 벤더 중립 |
| **OpenHands** | 자율 실행형 | 지원 | 사람이 안 보는 동안 길게 돌리는 용도 |

**로컬 구성이라면 `opencode` + Ollama/vLLM이 가장 마찰이 적습니다.**

```bash
# Ollama v0.15+ 는 한 줄로 끝납니다
ollama launch opencode --model qwen3-coder
```

vLLM에 붙일 때는 수동 설정:

```jsonc
// ~/.config/opencode/opencode.json
{
  "provider": {
    "local": {
      "npm": "@ai-sdk/openai-compatible",
      "options": { "baseURL": "http://localhost:8000/v1" },  // vLLM 포트
      "models": { "Qwen/Qwen3-Coder-30B-A3B-Instruct": {} }
    }
  }
}
```

## A-3. 로컬 에이전트의 함정 두 개

### ① 컨텍스트 기본값 4096

Ollama는 모델이 256K를 지원해도 **기본 컨텍스트를 4096으로 잘라버립니다.**
에이전트는 도구 정의 + 파일 내용 + 대화 이력이 모두 들어가야 하므로,
4096에서는 **파일 편집·bash 실행이 아예 동작하지 않습니다.**
opencode 문서 기준 최소 16K, 권장 64K 이상입니다.

```bash
OLLAMA_CONTEXT_LENGTH=65536 ollama serve          # Ollama
vllm serve ... --max-model-len 65536              # vLLM (→ 8단계)
```

여기서 **7단계의 KV 캐시 계산이 바로 실전이 됩니다.** 64K 컨텍스트가 몇 GB를 먹는지
계산할 수 있어야 `--gpu-memory-utilization` 값을 정할 수 있습니다.

### ② Tool calling 지원 여부

에이전트의 본질은 "모델이 도구를 호출하는 것"입니다.
**function call 포맷이 학습되지 않은 모델은 코딩 실력과 무관하게 에이전트로 쓸 수 없습니다.**
일반 채팅 모델을 붙이면 파일 편집이 무한 실패합니다.

## A-4. 3090 2대(48GB) 기준 모델 추천

**Qwen3-Coder-30B-A3B-Instruct** 가 이 구성에 잘 맞습니다.

- MoE (총 30B / **활성 3B**) → **18단계 개념 그대로.** 30B급 지식에 3B급 생성 속도
- SWE-bench 51.6, 네이티브 256K 컨텍스트 (YaRN으로 1M까지 확장 가능 → 15단계)
- tool calling이 명시적으로 수정·검증된 모델
- Q4_K_M 약 18.6GB → **48GB면 FP8로 올리고 컨텍스트도 넉넉히** 확보 가능

에이전트는 토큰을 대량으로 소모하므로 decode 속도가 곧 사용성입니다.
MoE의 "활성 파라미터만 연산한다"는 성질이 여기서 특히 유리합니다.

> 💡 **현실적 기대치**: 6단계의 "30 tok/s면 챗봇으로 쓸만하다"는 기준은 **에이전트에는 부족합니다.**
> 에이전트는 한 요청에 수천~수만 토큰을 생성하므로 체감상 100 tok/s 이상이 필요합니다.
> 로컬 코딩 에이전트가 클라우드보다 답답하게 느껴지는 원인은 대부분 이 지점입니다.

## A-5. Orca — 에이전트 오케스트레이터 (ADE)

**Agent Development Environment.** 코딩 에이전트를 만드는 도구가 아니라,
**여러 개를 동시에 돌리고 결과를 비교하는 조종석**입니다.

```
[기존]  터미널 하나 = 에이전트 하나 = 작업 하나 (순차)

[Orca]  작업A → worktree A → opencode     ┐
        작업B → worktree B → Claude Code  ├→ 나란히 진행, 승자를 머지
        작업C → worktree C → codex        ┘
```

핵심 아이디어는 **git worktree 격리**입니다. 각 에이전트가 저장소의 독립 복사본에서 작업하므로
서로 충돌하지 않습니다. 같은 문제를 다른 에이전트/다른 모델에 동시에 던져놓고 잘된 걸 채택할 수 있습니다.

- MIT 라이선스, 무료, macOS/Windows/Linux
- 40+ CLI 에이전트 래핑 (opencode, Claude Code, Codex, Grok 등)
- worktree별 Chromium 창 — UI 요소를 클릭해 HTML/CSS/스크린샷을 에이전트에 전달
- **터미널 TUI가 아니라 데스크톱 앱**입니다

> **로컬 LLM 맥락**: Orca 자체는 모델을 직접 쓰지 않습니다. 안에서 돌리는 opencode가 로컬 모델을 씁니다.
> 다만 **병렬 3개 = 동시 요청 3개**이므로 **7단계의 배치/KV 캐시 압박을 직접 맞게 됩니다.**
> 48GB에서 에이전트 3개를 동시에 돌리려면 배치와 컨텍스트를 계산해서 잡아야 합니다.

지금 단계에서 필수는 아닙니다. opencode가 손에 익은 뒤
"동시에 여러 접근을 시도하고 싶다"는 욕구가 생겼을 때 꺼내는 도구입니다.

## A-6. OpenClaw — 개인 비서 에이전트 (다른 카테고리)

**코딩 도구가 아닙니다.** 위 두 개와 계보가 다릅니다.

| | 코딩 에이전트 (opencode) | OpenClaw |
|---|---|---|
| 목적 | 코드베이스 수정 | 내 **일상 업무** 처리 |
| 인터페이스 | 터미널 TUI | **메신저** (WhatsApp, Telegram, Slack, Discord, Signal, iMessage) |
| 실행 방식 | 내가 켤 때 실행 | **상시 백그라운드** (heartbeat로 주기적 자율 판단) |
| 작업 대상 | 프로젝트 폴더 | 이메일, 캘린더, 브라우저, 로컬 파일, 연결 서비스 |
| 확장 | MCP, 도구 | **skills** |

```
"내일 오전 회의 정리해서 참석자들한테 메일 보내줘"
   → 캘린더 조회 → 관련 문서 검색 → 초안 작성 → 발송
   → 판단이 필요한 것만 텔레그램으로 되물음
```

자체 하드웨어에서 self-hosted로 돌아가며,
첫 커밋 5개월 만에 GitHub 36만 스타로 6번째 최다 스타 프로젝트가 됐습니다.

> ⚠️ **보안 주의**: OpenClaw는 관련 보안 논문이 유독 많습니다(안전성 분석, 프라이버시·윤리 리스크, 포렌식 분석).
> 이유는 구조적입니다 — **로컬 파일 + 셸 + 메신저 + 이메일 접근 권한을 가진 에이전트가
> 자율적으로 상시 실행**되면, 프롬프트 인젝션 한 번이 곧 계정 탈취입니다.
> 받은 메일 본문에 지시문이 숨어 있으면 그걸 읽은 에이전트가 실행할 수 있습니다.
> 쓸 거라면 격리된 환경에서, 권한을 최소로 시작하세요.

## A-7. 정리 — 무엇을 언제 쓰나

| 하고 싶은 것 | 도구 |
|---|---|
| 로컬 모델로 터미널에서 코딩 | **opencode + Ollama/vLLM** ← 여기서 시작 |
| 정밀한 Git 단위 편집 | aider |
| 코딩 넘어 시스템 자동화 | goose |
| 여러 에이전트 병렬 실행·비교 | Orca (나중에) |
| 개인 일상 업무 자동화 | OpenClaw (별개 목적, 보안 주의) |

**커리큘럼과의 연결**: opencode를 붙이는 순간 4~8단계가 전부 실전 문제로 바뀝니다.
컨텍스트를 얼마로 잡을지(8단계), KV 캐시가 얼마나 먹는지(7단계),
TPOT이 에이전트에 충분한지(6단계) — 이걸 계산할 수 있어야 제대로 세팅할 수 있습니다.
