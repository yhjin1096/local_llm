## 1. 이 단계는 무엇인가

### 원문의 요지

::: {.quote data-label="원문 (8단계) — Max sequence length를 늘려봅니다"}
- Context length와 거의 동일한 의미를 가집니다. **LLM의 단기 기억력**에 대한 설정 값입니다.
- **"4096, 8192, 16384, 32768로 올릴수록 얼마나 긴 내용까지 제대로 기억하는지 확인해봅니다.
  동시에 얼마나 메모리를 많이 먹는지 확인해봅니다."**
- **KV 캐시는 linear하게 늘어나는데 Attention 연산은 quadratic하게 늘어나는 것**도 확인합니다.
:::

::: {.quote data-label="원문 (9단계) — Parallelism을 돌려봅니다"}
- **Tensor Parallel (TP=2) vs Pipeline Parallel (PP=2)** 를 비교해봅니다.
- 칩이 여러 개 있을 때, 칩들에 **모델 가중치를 나눠서 올린다**거나,
  또는 **연산 순서를 여러 칩들에 나눠서 올리는** 테크닉을 익힙니다.
:::

### 두 단계를 왜 묶는가

7단계에서 이 비례식의 한 항을 흔들었습니다. 이제 나머지를 흔듭니다.

```
KV cache  ∝  컨텍스트 길이 × 동시 요청 수
                  ↑ 8단계        ↑ 7단계 (완료)
```

그리고 **그 곱셈을 어떻게 조절해도 안 되는 경우**가 있습니다.
모델 자체가 한 장에 안 들어가는 경우입니다. 그때의 답이 9단계입니다.

| 상황 | 답 | 단계 |
|---|---|---|
| 한 요청이 차지하는 자리가 너무 크다 | 컨텍스트를 조절한다 | **8단계** |
| 모델 가중치가 아예 안 들어간다 | **장비를 늘려 쪼갠다** | **9단계** |

두 단계 모두 *"안 들어갈 때 무엇을 할 수 있는가"* 라는 한 질문의 답이라 함께 봅니다.

::: warn
**9단계는 이 장비로 실습할 수 없습니다.** GPU(Graphics Processing Unit)가 두 대 이상이어야 하고, 우회할 방법이 없습니다.
1단계에서 이미 확인한 제약이며, 21단계 중 유일하게 막히는 단계입니다.

그렇다고 건너뛰지는 않습니다. 이유는 두 가지입니다.

1. **원문 전체가 3090 두 대를 전제**하므로, 개념을 모르면 원문의 다른 판단들을 읽을 수 없습니다
2. 나중에 장비를 늘리거나 클라우드를 빌릴 때 **무엇을 고를지 판단**해야 합니다

그래서 이 문서는 9단계를 **개념으로 다루고, 실측은 대안 경로를 제시**합니다 (3.2절).
:::

### 8단계에는 7단계에 없던 것이 하나 있다

7단계에서 요청 수를 늘렸을 때는 **메모리만** 늘었습니다. 컨텍스트는 다릅니다.

::: key
LLM(Large Language Model)에서 컨텍스트를 늘리면 **메모리와 연산이 함께** 늘어납니다.
그런데 **같은 속도로 늘지 않습니다.** 이 비대칭이 8단계의 전부입니다.
:::

### 이 문서를 읽고 나면 답할 수 있는 질문

1. 컨텍스트를 2배로 늘리면 KV cache 와 연산량은 각각 몇 배가 되는가?
2. 컨텍스트를 늘릴 때 **메모리가 먼저 터지는 상황**과 **TTFT(Time To First Token)가 먼저 터지는 상황**은 각각 언제인가?
3. "32K 를 지원한다"와 "32K 를 제대로 기억한다"는 왜 다른가?
4. 모델이 한 장에 안 들어갈 때 TP 와 PP 중 무엇을 왜 고르는가?
5. GPU 를 2배로 늘리면 왜 속도가 2배가 되지 않는가?

4절 확인 문제가 이 다섯 가지를 다시 묻습니다.

## 2. 개념

## 2.1 선형으로 느는 것과 제곱으로 느는 것 [완전]

컨텍스트를 늘렸을 때 늘어나는 비용은 **한 종류가 아닙니다.** 세 가지가 각각 다른 속도로 늡니다.

### 세 가지 비용

| 무엇이 | 어떻게 느는가 | 컨텍스트 2배면 |
|---|---|---|
| **KV cache 메모리** | 선형 — 토큰마다 한 벌씩 쌓임 | **2배** |
| **prefill 의 attention 연산** | **제곱** — 모든 토큰이 모든 토큰을 봄 | **4배** |
| decode 의 attention 연산 | 선형 — 새 토큰 1개가 기존 전부를 봄 | 2배 |

가운데 줄이 8단계의 주인공입니다. 왜 제곱인지는 세어보면 바로 나옵니다.

> 회의에 참석한 사람들이 **서로 한 번씩 악수**한다고 해봅시다.
> 사람이 2배가 되면 악수 횟수는 2배가 아니라 대략 4배가 됩니다.

실제로는 이렇습니다. attention 은 **각 토큰이 앞의 모든 토큰을 참조**하는 연산입니다.
prefill 은 입력 전체를 한꺼번에 처리하므로, 참조 관계의 개수가 곧 연산량이 됩니다.
토큰이 2배가 되면 **참조 관계는 대략 4배**입니다.

decode 는 다릅니다. 새 토큰 **하나**가 기존 토큰들을 볼 뿐이므로, 컨텍스트에 선형입니다.

::: calc
**컨텍스트별 비용 어림셈**

```
KV cache(GB)     ≈ 토큰당 KV 바이트 × 컨텍스트 × 동시 요청 수     ← 선형
prefill 상대 연산량 ∝ (컨텍스트)²                                  ← 제곱
```

내 장비의 주력 모델(Qwen3-8B, 토큰당 144 KB, 요청 1개) 기준으로 나란히 놓으면:

```
컨텍스트    KV cache        prefill 상대 연산량
  4,096      약 0.6 GB          1 배 (기준)
  8,192      약 1.1 GB          4 배
 16,384      약 2.3 GB         16 배
 32,768      약 4.5 GB         64 배
131,072      약 18  GB      1,024 배
```

메모리는 32배 늘어나는 동안 **연산은 1,024배** 늘어납니다.

**이 어림셈이 틀리는 경우**

- **prefill 연산에는 attention 말고 다른 부분도 있습니다.** 그쪽은 선형이라 짧은 컨텍스트에서는 제곱 항이 지배적이지 않습니다. 위 배율은 **컨텍스트가 충분히 길 때의 경향**입니다
- **선형 attention 을 섞은 하이브리드 모델**은 이 표가 통째로 다릅니다 (1단계 2.5절의 같은 단서)
- **Prefix Caching 이 걸리면** 이미 계산된 구간의 prefill 을 건너뜁니다 (7단계 2.6절). 그만큼 제곱 비용을 피합니다
- 위 KV 값은 **요청 1개** 기준입니다. 7단계에서 본 대로 요청 수만큼 곱해집니다
:::

::: key
원문이 *"KV 캐시는 linear 한데 Attention 연산은 quadratic"* 이라고 한 문장이 이 표입니다.
**컨텍스트를 늘릴 때 먼저 아파오는 것이 상황에 따라 다른 이유**가 여기서 나옵니다.
:::

## 2.2 그래서 무엇이 먼저 터지는가 [완전]

두 비용이 다른 속도로 늘어나므로, **무엇이 먼저 한계에 닿을지는 워크로드가 정합니다.**

| 상황 | 먼저 터지는 것 | 이유 |
|---|---|---|
| 동시 요청이 많다 | **메모리 (KV cache)** | KV 는 `컨텍스트 × 요청 수` 로 곱해짐 (7단계) |
| 긴 문서를 한 번에 넣는다 | **TTFT** | 요청은 하나뿐이라 메모리는 여유. 대신 prefill 이 제곱 |

::: note
같은 "컨텍스트를 늘렸다"인데 증상이 정반대로 나타납니다.

- 챗봇에 사용자가 몰리는 상황 — VRAM(Video Random Access Memory) 부족, preemption 로그
- 긴 코드베이스를 한 번에 리뷰시키는 상황 — 메모리는 멀쩡한데 **첫 응답이 하염없이 안 나옴**

전자는 7단계에서 본 증상이고, 후자가 8단계에서 새로 만나는 증상입니다.
:::

::: key
**"128K 컨텍스트 지원"은 "128K 를 다 채워 써도 된다"는 뜻이 아닙니다.**
채워 넣을 수는 있지만, 그 요청의 첫 응답을 기다릴 수 있느냐는 다른 문제입니다.
VRAM 과 인내심이 각각 따로 한계를 겁니다.
:::

## 2.3 선언한 컨텍스트와 실제로 기억하는 컨텍스트 [완전]

여기까지는 **비용** 이야기였습니다. 8단계에는 비용과 무관한 함정이 하나 더 있습니다.

1단계에서 컨텍스트 길이를 다루며 *"설정값은 상한 선언"* 이라고 했습니다. 그 이야기의 뒷면입니다.

::: key
모델이 32K 를 지원한다고 해서 **32K 전부를 균등하게 기억하지는 않습니다.**
이건 설정이나 장비의 문제가 아니라 **모델의 성질**입니다.
:::

알려진 경향이 하나 있습니다. 긴 컨텍스트에서 **앞부분과 뒷부분은 잘 참조하고 가운데는 흘리는** 현상입니다.
**Lost in the Middle** 이라고 부릅니다.

이걸 확인하는 표준적인 방법이 **NIAH(Needle In A Haystack)** 테스트입니다.
긴 더미 텍스트("건초더미") 안에 특정 문장("바늘")을 심고, 그것을 찾아내는지 봅니다.
심는 **위치**와 전체 **길이**를 격자로 바꿔가며 반복하면 어디서 무너지는지가 드러납니다.

::: note
2–3단계에서 만든 평가 습관이 여기서 다시 쓰입니다.
NIAH 도 결국 **문항을 만들고, 모델에 넣고, 답을 채점하는** 루프입니다 (2–3단계 2.1절).
다른 점은 문항이 "지식"이 아니라 **"위치"** 를 묻는다는 것뿐입니다.
:::

::: warn
이 테스트의 결과를 **정확도 벤치마크와 섞어 읽으면 안 됩니다.**
MMLU Pro 점수가 좋은 모델이 긴 컨텍스트의 가운데를 잘 기억한다는 보장은 없습니다.
**다른 능력을 재는 다른 자**입니다.
:::

## 2.4 컨텍스트를 억지로 늘리는 기술 [씨앗]

모델이 학습된 것보다 긴 컨텍스트를 쓰게 만드는 기법들이 있습니다.
**RoPE(Rotary Position Embedding) scaling**, **YaRN(Yet another RoPE extensioN)** 같은 이름으로 불립니다.

원리만 잡아둡니다. 모델은 토큰의 **위치 정보**를 특정 방식으로 인코딩해 학습하는데,
그 인코딩을 늘리거나 다시 스케일해서 **학습 때 본 적 없는 길이까지 밀어 넣는** 것입니다.

공짜가 아닙니다. **학습 때 본 적 없는 구간이므로 그 영역의 품질이 떨어집니다.**
"컨텍스트를 늘렸다"와 "그 길이를 제대로 쓴다"가 갈라지는 또 하나의 지점입니다.

::: later
RoPE scaling · YaRN · Sliding Window Attention 같은 long context 기법들의 지도는 **15단계**입니다.
각 기법이 "무엇을 해결하려고 나왔는가"만 잡는 단계이고, 원문도 그 이상은 요구하지 않습니다.
8단계에서는 **"늘리는 기술이 있고, 늘린 구간은 품질이 다르다"** 까지면 충분합니다.
:::

## 2.5 컨텍스트가 부담이면 쓸 수 있는 카드 [완전]

1단계 2.5절에서 KV cache 의 세 손잡이를 봤습니다. 그중 하나가 여기서 실전에 쓰입니다.

**KV cache 저장 정밀도를 낮추는 것**입니다. 공식의 마지막 항이 절반이 되므로 **KV cache 가 절반**이 됩니다.

```
FP16 저장 → 토큰당 약 144 KB → 32K 컨텍스트에 약 4.5 GB
FP8  저장 → 토큰당 약  72 KB → 32K 컨텍스트에 약 2.3 GB
```

::: key
이 카드는 **메모리 쪽만 해결합니다.** prefill 의 제곱 연산은 그대로입니다.
2.2절의 두 증상 중 **"동시 요청이 많아 메모리가 터지는 쪽"** 에만 듣습니다.
:::

::: note
원문 8단계는 이 설정을 시도해보라고 권하면서, **품질 영향을 3단계 평가로 재보라**고 덧붙입니다.
2–3단계에서 만든 비교표가 여기서 또 쓰입니다 — 같은 자로 재야 손실이 얼마인지 말할 수 있습니다.

내 장비는 Blackwell 이라 FP8 이 하드웨어 가속 대상입니다 (1단계 2.6절).
다만 KV cache 를 FP8 로 **저장**하는 것은 일차적으로 공간을 아끼는 선택입니다.
:::

::: later
KV cache 정밀도를 낮췄을 때 답이 실제로 얼마나 나빠지는지, 그 손익 판단은 **16단계**입니다.
8단계에서는 **"메모리 쪽 카드가 하나 있고, 연산 쪽에는 듣지 않는다"** 까지면 충분합니다.
:::

## 2.6 모델이 아예 안 들어갈 때 — 쪼개는 두 방향 [완전]

여기서부터 9단계입니다. 앞의 모든 조절은 **모델이 한 장에 올라간다는 전제** 위에 있었습니다.
그 전제가 깨지면 답은 하나뿐입니다. **장비를 늘려서 모델을 나눠 올립니다.**

### 두 방식의 성격

| | **Tensor Parallel (TP)** | **Pipeline Parallel (PP)** |
|---|---|---|
| 쪼개는 대상 | 각 레이어의 가중치 행렬 | 레이어 묶음 |
| GPU 간 통신 | **레이어마다** (많음) | 스테이지 경계에서만 (적음) |
| 필요한 연결 속도 | 높음 — NVLink 권장 | 낮음 — PCIe(Peripheral Component Interconnect Express)로도 견딤 |
| 단일 요청 지연시간 | **낮음** (두 GPU 가 동시에 일함) | 높음 (순차 통과) |
| 노는 자원 | 적음 | **파이프라인 버블** 발생 |
| 잘 맞는 상황 | 한 대 안, 빠른 연결 | 여러 대에 걸침, 느린 연결 |

::: key
선택 기준은 **GPU 사이의 통로가 얼마나 빠른가** 하나로 거의 정해집니다.
TP 는 통신을 많이 하므로 빠른 통로가 있어야 하고, PP 는 통신이 적어 느린 통로에서도 견딥니다.
:::

::: note
TP 에는 제약이 하나 더 있습니다. 레이어를 균등하게 쪼개야 하므로,
**GPU 수가 attention 헤드 수의 약수**여야 합니다. 그래서 보통 2, 4, 8 을 씁니다.
:::

## 2.7 통신 비용과 파이프라인 버블 [완전]

1단계에서 *"GPU 두 대는 정말 두 배인가"* 를 물으며 씨앗을 남겼습니다. 여기서 답합니다.
**두 배가 되지 않습니다.** 이유가 두 방식에서 각각 다릅니다.

### TP 의 비용 — 통신

레이어마다 두 GPU 가 중간 결과를 주고받습니다. 그 시간 동안은 계산이 진행되지 않습니다.

1단계에서 본 통로별 속도를 다시 보면 왜 이게 문제인지 보입니다.

| 경로 | 대역폭 |
|---|---|
| GPU 내부 (VRAM ↔ 연산 유닛) | 약 1,792 GB/s |
| **NVLink** (3090) | 약 112 GB/s |
| **PCIe 4.0 x16** | 약 32 GB/s |

GPU 안에서 데이터를 옮기는 것보다 **GPU 사이로 옮기는 것이 자릿수로 느립니다.**
그 느린 통로를 레이어마다 지나가야 하는 것이 TP 입니다.

### PP 의 비용 — 버블

PP 는 통신이 적은 대신 다른 낭비가 있습니다. **앞 GPU 가 일하는 동안 뒤 GPU 가 논다**는 것입니다.

## 2.8 병렬화는 속도가 아니라 용량을 위한 것 [완전]

원문이 9단계에 붙인 단서가 이 절의 요지입니다.

::: {.quote data-label="원문 (9단계)"}
병렬화는 "속도를 위해" 하는 게 아니라 **"안 들어가는 모델을 넣기 위해"** 먼저 합니다.
:::

앞 절에서 본 대로 **속도는 오히려 손해**를 봅니다. 그런데도 하는 이유는
**혼자서는 못 하던 것이 가능해지기 때문**입니다.

| 목적 | 병렬화로 되는가 |
|---|---|
| 안 들어가던 모델을 올린다 | ✅ 이것이 본래 목적 |
| 동시 요청을 더 받는다 | ✅ KV cache 자리가 늘어남 |
| 같은 모델을 더 빠르게 돌린다 | 🔶 통신·버블 때문에 기대만큼 안 됨 |

::: note
이 판단은 1단계의 결론과 이어집니다. 1단계에서 *"공부를 할 수 있을 만큼의 VRAM을 쫓아야 한다"* 는
원문의 문장을 봤습니다. 병렬화도 같은 이야기입니다 — **속도가 아니라 범위를 사는 것**입니다.
:::

### 그래서 비교 대상이 하나 더 있다

원문은 관찰 포인트에 이것을 넣어뒀습니다. **양자화와의 비교**입니다.

| 방법 | 14B 모델을 돌리는 두 가지 길 |
|---|---|
| 한 장 + 양자화 | 정밀도를 낮춰 한 장에 욱여넣음 — **정확도를 냄** |
| 두 장 + 병렬화 | 원본 정밀도 그대로 나눠 올림 — **속도와 장비를 냄** |

::: key
"안 들어간다"에 대한 답이 **양자화만 있는 게 아닙니다.**
3단계에서 정확도를 내주고 용량을 샀다면, 9단계는 **장비와 속도를 내주고 정확도를 지키는** 선택지입니다.
어느 쪽이 맞는지는 무엇을 아끼고 싶은지에 달렸습니다.
:::

## 3. 내 장비 기준 정리

### 3.1 8단계 — 전부 가능합니다

컨텍스트 실험은 GPU 한 장으로 충분합니다. 오히려 변수가 적어 해석이 단순합니다.

| 컨텍스트 | KV cache (요청 1개) | 32GB 에서 |
|---|---|---|
| 4K | 약 0.6 GB | ✅ 여유 |
| 8K | 약 1.1 GB | ✅ 여유 |
| 16K | 약 2.3 GB | ✅ 여유 |
| 32K | 약 4.5 GB | ✅ 가능 — 8B BF16(16GB) 과 합쳐도 예산 안 |
| 128K | 약 18 GB | 🔶 가중치와 합치면 34GB — **BF16 으로는 불가** |

::: note
마지막 줄이 8단계에서 직접 만나게 될 벽입니다.
여기서 선택지가 갈립니다 — 가중치를 양자화하거나(3단계 카드), KV 를 FP8 로 낮추거나(2.5절 카드),
컨텍스트를 포기하거나. **세 카드가 모두 앞 단계에서 배운 것**입니다.
:::

### 3.2 9단계 — 실습 불가, 대안은 있습니다

**GPU 1대로는 TP 도 PP 도 성립하지 않습니다.** 1단계에서 확인한 유일한 제약입니다.

| 대안 | 내용 |
|---|---|
| **클라우드 시간 대여** | 9단계 실습만 몇 시간. 다중 GPU 인스턴스로 TP=2 / PP=2 비교 |
| 부수 효과 | 같은 방법으로 70B 급, 멀티 노드 실습까지 가능 |
| 준비물 | **내 5090 측정값을 기준선으로 갖고 갈 것** — 비교 대상이 있어야 학습이 됨 |

::: warn
장비를 늘려도 원문과 같은 조건이 되지 않습니다. **5090 에는 NVLink 가 없습니다.**

TP 는 통신이 많아 빠른 통로가 필요한데, NVLink 없이 PCIe 만 쓰면 **TP 가 상대적으로 불리**합니다.
원문이 신형 대신 3090 을 고집한 숨은 이유 중 하나가 이것입니다 (1단계 2.7절).
:::

### 3.3 원문 전제와의 차이

| 항목 | 원문 (3090 24GB × 2) | 내 장비 (5090 32GB × 1) |
|---|---|---|
| 8단계 컨텍스트 실험 | 한 장 24GB 기준 — 32K 가 빠듯 | ✅ **32GB 라 여유** |
| 128K 컨텍스트 | 두 장을 묶으면 여지 있음 | 🔶 BF16 으로는 불가, 카드가 필요 |
| 9단계 TP / PP | ✅ 가능 (NVLink 있음) | ❌ **불가** — 클라우드 대안 |
| prefill 연산 성능 | 약 142 TFLOPS/장 | **약 419 TFLOPS** — 제곱 벽이 늦게 옴 |

::: key
8단계는 **내 장비가 원문보다 유리**합니다. VRAM 도 연산 성능도 앞섭니다.
9단계는 **유일하게 불리한 단계**이고, 그것도 성능이 아니라 **대수의 문제**입니다.
:::

## 4. 확인 문제

::: quiz
1. **컨텍스트를 8K 에서 32K 로 늘리면 KV cache 와 prefill 연산량은 각각 몇 배가 되는가?**

   <details><summary>답</summary>

   컨텍스트가 **4배**가 되었습니다.

   ```
   KV cache      선형 → 4 배      (약 1.1 GB → 약 4.5 GB)
   prefill 연산  제곱 → 16 배     (4² = 16)
   ```

   메모리는 4배인데 연산은 16배입니다.
   그래서 컨텍스트를 늘릴 때 **VRAM 은 아직 여유가 있는데 TTFT 가 먼저 못 견디는** 상황이 생깁니다.

   </details>

2. **왜 prefill 은 제곱이고 decode 는 선형인가?**

   <details><summary>답</summary>

   **참조 관계의 개수를 세어보면 나옵니다.**

   - **prefill** — 입력 전체를 한꺼번에 처리합니다. 각 토큰이 앞의 모든 토큰을 참조하므로, 토큰이 2배가 되면 참조 관계는 대략 4배가 됩니다. 사람이 2배가 되면 악수 횟수가 4배가 되는 것과 같습니다
   - **decode** — 새로 만드는 토큰은 **하나**입니다. 그 하나가 기존 토큰 전부를 볼 뿐이므로, 컨텍스트에 선형입니다

   차이를 만드는 것은 **한 번에 처리하는 토큰이 전체인가 하나인가**입니다.
   4–6단계에서 두 구간의 병목이 갈린 이유와 같은 뿌리입니다.

   </details>

3. **컨텍스트를 늘렸더니 VRAM 은 여유가 있는데 첫 응답이 몹시 느려졌습니다. 무엇이 일어난 것이며, KV cache 를 FP8 로 낮추면 해결되는가?**

   <details><summary>답</summary>

   **prefill 의 제곱 비용**에 걸린 것입니다. 요청이 하나뿐이라 메모리는 여유롭지만,
   입력이 길어 attention 연산이 급격히 늘어난 상태입니다. TTFT 는 prefill 이 정합니다(4–6단계 2.4절).

   **FP8 KV cache 로는 해결되지 않습니다.** 그 카드는 **메모리 쪽만** 줄입니다.
   저장 정밀도를 낮춰도 계산해야 할 참조 관계의 개수는 그대로입니다.

   이 상황에서 유효한 방향은 다릅니다 — 입력을 줄이거나, 이미 계산된 접두부를 재사용하거나
   (Prefix Caching, 7단계 2.6절), 연산 성능이 더 높은 장비를 쓰는 쪽입니다.

   </details>

4. **"이 모델은 128K 컨텍스트를 지원합니다"라는 문장에서 확인해야 할 것 두 가지는?**

   <details><summary>답</summary>

   1. **내 장비에 들어가는가** — 128K 면 KV cache 만 약 18GB 입니다. 8B BF16 가중치 16GB 와 합치면 32GB 를 넘깁니다. 지원 여부와 내가 쓸 수 있는지는 다른 문제입니다
   2. **그 길이를 제대로 기억하는가** — 선언된 컨텍스트와 실제로 참조되는 컨텍스트는 다릅니다. 긴 컨텍스트의 가운데를 흘리는 경향(Lost in the Middle)이 알려져 있고, NIAH 테스트로 확인합니다

   덧붙여, 그 길이가 **RoPE scaling 같은 기법으로 늘린 것**이라면 확장 구간의 품질이 특히 다를 수 있습니다.

   </details>

5. **TP 와 PP 중 무엇을 고를지는 무엇을 보고 판단하는가?**

   <details><summary>답</summary>

   **GPU 사이의 통로가 얼마나 빠른가**가 거의 결정합니다.

   - TP 는 **레이어마다** 통신합니다 → 빠른 연결(NVLink 등)이 있어야 제 성능이 납니다. 대신 두 GPU 가 동시에 일하므로 **단일 요청 지연시간이 유리**합니다
   - PP 는 **스테이지 경계에서만** 통신합니다 → 느린 연결에서도 견딥니다. 대신 파이프라인 버블로 자원이 놉니다

   실전 규칙으로는 **한 대 안에서 빠르게 묶여 있으면 TP, 느린 연결이거나 여러 대에 걸치면 PP** 입니다.
   TP 는 추가로 **GPU 수가 attention 헤드 수의 약수**여야 한다는 제약이 있습니다.

   </details>

6. **GPU 를 2대로 늘리면 왜 속도가 2배가 되지 않는가?** 두 방식에서 각각의 이유를 드세요.

   <details><summary>답</summary>

   - **TP — 통신 비용.** GPU 내부는 약 1,792 GB/s 인데 GPU 사이는 NVLink 라도 약 112 GB/s, PCIe 면 약 32 GB/s 입니다. 자릿수로 느린 통로를 **레이어마다** 지나가야 하고, 그동안 계산은 멈춰 있습니다
   - **PP — 파이프라인 버블.** 앞 GPU 가 일하는 동안 뒤 GPU 가 놉니다. 파이프라인이 채워지기 전과 비워진 뒤에 빈 구간이 남습니다. 작업을 잘게 쪼개면 줄지만 없어지지는 않습니다

   그래서 병렬화의 목적은 속도가 아니라 **안 들어가는 모델을 넣는 것**입니다.

   </details>

7. **14B 모델을 돌리는 두 가지 길 — "한 장 + 양자화" 와 "두 장 + 병렬화" 는 각각 무엇을 대가로 내는가?**

   <details><summary>답</summary>

   | 방법 | 얻는 것 | 내주는 것 |
   |---|---|---|
   | 한 장 + 양자화 | 장비 추가 없이 올림 | **정확도** (3단계에서 잰 그 손실) |
   | 두 장 + 병렬화 | 원본 정밀도 유지 | **장비 비용 + 속도** (통신·버블) |

   "안 들어간다"에 대한 답이 양자화 하나가 아니라는 점이 중요합니다.
   무엇을 아끼고 싶은지에 따라 선택이 갈립니다.

   </details>

8. **내 장비(5090 한 대)로 9단계를 실습할 수 없는 이유는 무엇이고, 대안은?** 그리고 나중에 5090 을 한 장 더 사면 원문과 같은 조건이 되는가?

   <details><summary>답</summary>

   **GPU 가 한 대이기 때문**입니다. TP 도 PP 도 나눠 올릴 대상이 둘 이상이어야 성립합니다.
   양자화나 설정으로 우회할 수 있는 종류의 제약이 아닙니다.

   대안은 **클라우드에서 다중 GPU 인스턴스를 몇 시간 빌리는 것**입니다.
   이때 내 5090 측정값을 기준선으로 갖고 가면 비교가 그대로 학습이 됩니다.

   **한 장을 더 사도 원문과 같은 조건은 아닙니다.** 5090 에는 NVLink 가 없기 때문입니다.
   3090 두 장은 NVLink 로 약 112 GB/s 로 묶이지만, 5090 두 장은 PCIe(약 32 GB/s)만 씁니다.
   통신이 많은 TP 쪽에서 원문보다 불리한 조건이 됩니다.

   </details>
:::

::: note
2.1절에서 prefill 의 제곱 비용을 봤습니다.
이 비용을 **연산량이 아니라 메모리 접근 방식** 쪽에서 공략하는 기법군이 있습니다.
Flash Attention 계열이고, 15단계의 지도에 나옵니다.
8–9단계에서는 **"제곱이라는 성질 자체는 남지만, 다루는 방법이 있다"** 까지만 알아두면 됩니다.
:::

### 10단계로 넘어가기 전에

10단계는 **LoRA / QLoRA 파인튜닝** — 이 커리큘럼에서 유일하게 **학습**을 하는 단계입니다.
지금까지 8개 단계에서 쌓은 것이 거의 통하지 않는 새 영역입니다.

다만 이어지는 것이 하나 있습니다. **VRAM 예산 계산**입니다.

::: key
1단계에서 *"학습은 추론보다 메모리를 5~6배 쓴다"* 고 표로만 보고 넘어갔습니다.
10단계는 그 배율을 실제로 만나는 자리입니다.

지금까지의 예산 계산이 `가중치 + KV cache` 였다면, 학습에는 **다른 항목들이 추가**됩니다.
그것이 왜 5~6배인지, 그리고 LoRA 가 그 배율의 어디를 잘라내는지가 10단계의 주제입니다.
:::

Phase 3 가 끝났습니다. 7 · 8 · 9단계에서 흔든 것을 정리하면 이렇습니다.

```
KV cache  ∝  컨텍스트 길이 × 동시 요청 수     ← 7·8단계에서 각각 흔듦
가중치     =  파라미터 수 × 정밀도             ← 3단계(양자화) · 9단계(쪼개기)
```

**서빙에서 조절할 수 있는 것은 결국 이 두 줄**이고, Phase 3 에서 그 손잡이를 모두 만져봤습니다.
