# 스터디 자료 작성 기준

이 문서는 `study/` 안의 스터디 자료를 **어떤 원칙으로 쓸지** 정한 규칙서입니다.
자료 자체가 아니라 **자료를 만드는 기준**입니다.

- 상위 커리큘럼: [`../README.md`](../README.md) — 원문 21단계 커리큘럼
- 빌드 도구: [`build/README.md`](build/README.md) — 마크다운 → HTML 변환 방법

---

## 0. 이 기준이 필요한 이유

커리큘럼 원문(`../README.md`)은 **이미 배경 지식이 있는 사람**을 대상으로 씌어 있습니다.
`"24GB면 8B BF16은 되지만 KV 캐시 여유가 빠듯하다"` 같은 문장 하나에
정밀도·가중치 용량 공식·VRAM 예산·KV 캐시가 전부 압축돼 있습니다.

스터디 자료의 역할은 그 압축을 푸는 것입니다. 그런데 압축을 풀다 보면 두 가지 실패가 생깁니다.

| 실패 유형 | 증상 |
|---|---|
| **무한 소급** | VRAM → KV 캐시 → attention → transformer → … 로 끝없이 파고들어 1단계 문서가 7단계를 삼킴 |
| **선점** | 뒤 단계에서 직접 실험해 깨달아야 할 결론을 미리 알려줘 그 단계의 학습 효과를 없앰 |

이 문서의 규칙 대부분은 **이 두 실패를 막기 위한 것**입니다.

## 3. 깊이 규칙 — `[완전]` 과 `[씨앗]`

이 자료의 가장 중요한 규칙입니다.

### 3.1 정의

| 표기 | 뜻 | 도달 지점 |
|---|---|---|
| `[완전]` | 이 단계에서 **끝까지** 이해해야 하는 개념 | 스스로 계산하거나 남에게 설명할 수 있음 |
| `[씨앗]` | 이 단계에서는 **방향만** 잡고 뒤 단계에 넘기는 개념 | "무엇을 해결하는 개념인지" 한 문장으로 말할 수 있음 |

### 3.2 `[씨앗]` 의 도달점 — 옵션 B

`[씨앗]` 개념은 **비유로 원리를 이해하는 지점까지** 씁니다. 구체적으로는 이렇습니다.

| 수준 | 쓰는가 | 예 (KV cache) |
|---|---|---|
| 존재 언급 | ✅ 필수 | "가중치 말고도 VRAM 을 먹는 게 있다" |
| 왜 존재하는가 (비유) | ✅ 필수 | "소설가의 요약 노트" |
| 무엇에 비례하는가 (정성적) | ✅ 필수 | "컨텍스트 × 동시 요청 수에 비례한다" |
| 정성적 결론 | ✅ 필수 | "가중치만 세면 VRAM 예산이 틀린다" |
| 정확한 공식 | ❌ 금지 | `2 × L × H_kv × D_head × ...` |
| 구체적 수치 계산 | ❌ 금지 | "8K 컨텍스트에 동시 8명이면 9GB" |
| 해결 기법 이름 | △ 이름만 | "GQA, PagedAttention 같은 기법이 있다" (설명 없이) |

즉 **"왜 그런 일이 벌어지는가"는 쓰고, "얼마인가"는 쓰지 않습니다.**

### 3.3 위임은 반드시 명시한다

`[씨앗]` 개념을 다룬 절은 **어디서 이어지는지 명시하고 끝냅니다.** `::: later` 콜아웃을 씁니다.

```markdown
::: later
정확한 KV cache 공식과 그것을 줄이는 기법은 **7단계**에서 다룹니다.
1단계에서는 "VRAM 예산을 세울 때 가중치만 세면 틀린다"까지 알면 충분합니다.
:::
```

이 콜아웃에는 두 가지를 반드시 담습니다.

1. **어느 단계로 넘기는가** (단계 번호)
2. **이 단계에서 알아야 할 것은 정확히 무엇까지인가**

2번이 없으면 독자는 "내가 덜 이해한 건가"에서 멈춥니다.

### 3.4 선점 금지

뒤 단계의 **실습 결론을 미리 쓰지 않습니다.** 이건 위 3.2 표의 "금지" 항목과 다른 층위의 규칙입니다.

| 상황 | 판단 |
|---|---|
| "배치를 키우면 메모리가 곱셈으로 늘어난다" | ✅ 원리이므로 씀 |
| "배치 32에서는 37GB 를 먹어 터진다" | ❌ 7단계가 직접 터뜨려 볼 내용 |
| "양자화하면 정확도가 떨어진다" | ✅ 원리이므로 씀 |
| "Q4 는 MMLU Pro 에서 몇 점 떨어진다" | ❌ 3단계가 직접 측정할 내용 |

판단 기준: **그 숫자를 직접 보는 것이 뒤 단계의 체크포인트인가?** 그렇다면 쓰지 않습니다.

## 4. 문체 규칙

### 4.1 용어 표기

원칙: **본문은 한글, 기술 용어는 영문 우선.**

```
✅ VRAM(Video Random Access Memory)은 GPU 기판에 붙은 전용 메모리입니다.
✅ 이후 VRAM 용량이 모든 판단의 기준이 됩니다.
✅ memory bandwidth(메모리 대역폭)가 병목입니다.

❌ 브이램은 지피유에 붙은 메모리입니다.
❌ 비디오 랜덤 액세스 메모리
```

**약어는 첫 등장 시 full name 을 반드시 1회 씁니다.** 이후에는 약어만 씁니다.

| 약어 | 첫 등장 시 표기 |
|---|---|
| VRAM | VRAM(Video Random Access Memory) |
| TDP | TDP(Thermal Design Power) |
| PCIe | PCIe(Peripheral Component Interconnect Express) |
| BF16 | BF16(Brain Floating Point 16) |
| GQA | GQA(Grouped Query Attention) |
| TTFT | TTFT(Time To First Token) |
| SM | SM(Streaming Multiprocessor) |
| CUDA | CUDA(Compute Unified Device Architecture) |

문서 맨 끝에 **용어표**를 둡니다 (6절 구조 참고). full name 을 잊었을 때 되돌아올 자리입니다.

### 4.2 비유 규칙

비유는 이 자료의 주된 설명 수단입니다. 다만 세 가지를 지킵니다.

1. **비유 뒤에 반드시 사실 문장을 붙입니다.** 비유만 남기면 독자가 비유를 사실로 기억합니다.
   ```markdown
   > 소설을 이어 쓰는 작가는 앞의 300페이지를 매번 다시 읽지 않고 요약 노트를 펼쳐둡니다.

   실제로는 각 토큰의 Key / Value 벡터를 저장해두고 재사용하는 것입니다.
   ```
2. **비유가 깨지는 지점을 밝힙니다.** 특히 오해를 유발할 비유는 한 줄로 한계를 적습니다.
3. **한 개념에 비유는 하나.** 두 개를 겹치면 둘 다 흐려집니다.

### 4.3 어림셈 규칙

**어림셈은 쓰고, 정확한 계산은 쓰지 않습니다.**

| 성질 | 어림셈 | 정확한 계산 |
|---|---|---|
| 목적 | 자릿수 감각 | 설정값 결정 |
| 표현 | `≈`, `대략`, `~` | `=` |
| 이 자료 | ✅ | ❌ (실행 환경 디렉터리의 몫) |

어림셈은 `::: calc` 콜아웃에 담고, **반드시 다음 세 가지를 함께 적습니다.**

1. 공식
2. 이 장비(5090 32GB)에 대입한 예 1개
3. **이 어림셈이 틀리는 조건** (예: MoE 모델, GQA 가 없는 구형 모델)

3번이 규칙에 들어간 이유는, 어림셈을 공식으로 오해하면 뒤 단계에서 계속 틀린 결론을 내기 때문입니다.

### 4.4 하지 말 것

| 금지 | 이유 |
|---|---|
| "간단히 말하면", "쉽게 말해서" 남용 | 실제로 간단해진 게 없으면 독자를 속임 |
| 근거 없는 수치 | 출처나 계산 과정이 없는 숫자는 넣지 않음 |
| "나중에 배웁니다" 로만 끝내기 | 3.3 규칙 위반. 어느 단계인지, 지금 필요한 건 어디까지인지 명시 |
| 원문에 없는 주장을 원문처럼 서술 | 원문 인용은 `::: quote` 로 구분 (아래 9.2) |
| 3090 기준 수치를 그대로 옮기기 | 5절 위반 |

## 5. 하드웨어 전제

모든 계산과 예시는 **실제 장비 기준**으로 씁니다.

| 항목 | 값 |
|---|---|
| GPU | NVIDIA GeForce RTX 5090 |
| VRAM | 32 GB GDDR7 |
| 아키텍처 | Blackwell |
| Compute Capability | sm_120 |
| 개수 | **1대** |
| 드라이버 | 580.173.02 |

### 5.1 원문 전제와의 차이를 다루는 방법

원문(`../README.md`)은 **RTX 3090 24GB × 2 = 48GB** 를 전제합니다. 이 차이는 무시하지 않고 명시적으로 다룹니다.

| 원칙 | 방법 |
|---|---|
| 본문의 모든 수치 | **5090 32GB × 1 기준으로 재계산** |
| 원문 전제가 근거로 필요할 때 | `::: quote` 로 원문을 인용한 뒤, 바로 아래에서 내 장비 기준으로 다시 계산 |
| 내 장비가 **유리한** 지점 | 명시 (예: FP8 / FP4 하드웨어 가속이 있음) |
| 내 장비가 **불리한** 지점 | 명시 (예: 48GB 가 아니라 32GB, NVLink 없음, GPU 1대) |
| 실습이 **불가능한** 단계 | 해당 단계 문서에서 대안 제시 (클라우드 대여 등) |

### 5.2 이미 파악된 차이

`ollama/README.md` 에 정리된 내용을 기준선으로 삼습니다.

- **9단계(Tensor / Pipeline Parallel)는 GPU 1대라 실습 불가** — 나머지 20단계는 가능
- 3090(Ampere)에 없는 **FP8 / NVFP4 하드웨어 가속이 있음** → 3단계·16단계에서 유리
- 32GB 면 **8B BF16(16GB) 원본을 여유롭게 돌릴 수 있음** → 3단계 비교의 기준선 확보 가능
- 4090·5090 에는 **NVLink 가 없음** → 향후 2대로 확장하더라도 원문과 조건이 다름

## 6. 문서 구조 템플릿

단계별 문서는 아래 순서를 따릅니다. 필요 없는 절은 빼되, **순서는 바꾸지 않습니다.**

```
YAML 머리말  (title / subtitle / eyebrow / meta / footer)

1. 이 단계는 무엇인가
   - 원문의 요지          ::: quote
   - 내 상황에서의 재해석
   - 이 문서를 읽고 나면 답할 수 있는 질문 3~5개   ← 문서의 목표를 먼저 보여줌

2. 개념  (계층 순서대로, 각 절 제목에 [완전]/[씨앗] 배지)
   2.1 …
   2.2 …
       - 비유 → 사실
       - 도식 (inline SVG)
       - ::: calc / ::: key / ::: later

3. 내 장비 기준 정리
   - 5090 32GB × 1 로 무엇이 되고 무엇이 안 되는가 (표)
   - 원문 전제와의 차이 (표)

4. 확인 문제        ::: quiz

5. 다음 단계로
   - 이 문서에서 [씨앗]으로 남긴 것들이 어느 단계로 이어지는지 (표)

6. 용어표
   - 이 문서에 등장한 약어 · full name · 한 줄 뜻
```

### 6.1 "읽고 나면 답할 수 있는 질문" 규칙

1절 끝에 두는 3~5개 질문은 **4절 확인 문제와 짝을 이룹니다.**
문서 앞에서 목표를 제시하고, 뒤에서 같은 것을 검증하는 구조입니다.

## 7. 확인 문제 규칙

| 항목 | 규칙 |
|---|---|
| 개수 | 단계당 5~8개 |
| 형식 | 서술형 위주. 객관식은 쓰지 않음 |
| 답 | `<details>` 로 접어서 **함께 제공** (별도 파일로 분리하지 않음) |
| 범위 | **`[완전]` 개념만 출제.** `[씨앗]` 은 출제하지 않음 |
| 유형 배분 | 아래 표 |

| 유형 | 개수 | 예 |
|---|---|---|
| 어림셈 계산 | 2~3 | "14B 모델을 BF16 으로 올리면 32GB 에 들어가는가?" |
| 개념 구분 | 1~2 | "TFLOPS 가 높은데 느린 상황이 왜 생기는가?" |
| 판단 근거 | 1~2 | "왜 4090 이 3090 의 대안이 되지 못한다고 하는가?" |
| 함정 | 1 | "`nvidia-smi` 의 GPU-Util 100% 는 GPU 를 잘 쓰고 있다는 뜻인가?" |

답에는 **결론만 쓰지 않고 근거를 씁니다.** 계산 문제는 계산 과정을 보여줍니다.

## 8. 다이어그램 규칙

| 항목 | 규칙 |
|---|---|
| 형식 | **inline SVG**. 외부 이미지 파일을 만들지 않음 |
| 색 | 하드코딩 금지. `s-fg` / `s-box` / `s-line` 등 클래스만 사용 (테마 연동) |
| 텍스트 | SVG 안의 글자는 최소화. 긴 설명은 `<figcaption>` 이나 본문으로 |
| 개수 | 단계당 3~6개. 개념 하나에 도식 하나 |
| 대체 텍스트 | `role="img"` + `aria-label` 필수 |
| ASCII 도식 | 흐름·비교처럼 정렬이 중요한 것은 코드블록 ASCII 로도 가능 (원문 스타일과 일관) |

다이어그램을 넣는 판단 기준: **글로 두 문단 이상 걸리는 구조적 관계**일 때만 넣습니다.
장식용 그림은 넣지 않습니다.

### 8.1 반드시 지켜야 하는 작성 형식

다이어그램은 **pandoc raw attribute 펜스(` ```{=html} `) 안에** 넣습니다.

````markdown
```{=html}
<figure>
<div class="svg-scroll">
<svg viewBox="0 0 720 240" role="img" aria-label="설명">
  ...
</svg>
</div>
<figcaption>캡션</figcaption>
</figure>
```
````

이 형식이 **선택이 아니라 필수**인 이유가 있습니다.

> ⚠️ 펜스 없이 SVG 를 그냥 쓰면, pandoc 의 `markdown_in_html_blocks` 규칙이 HTML 블록 내부를
> **마크다운으로 재파싱**합니다. 그 결과 SVG 중간에 `<p>` 와 `</div>` 가 끼어들어
> **XML 이 깨지고 그림이 렌더링되지 않습니다.**
> 빈 줄이 있으면 블록 자체가 끊어져 더 심하게 깨집니다.
>
> 증상이 조용합니다 — 빌드는 성공하고, 브라우저는 그림만 안 보여줍니다.
> 그래서 형식으로 강제합니다.

부수 규칙 두 가지.

- **가로 스크롤 컨테이너(`<div class="svg-scroll">`)를 원문에 직접 씁니다.** 필터가 자동으로 감싸지 않습니다
- SVG 안에서 `<defs>` 의 `marker id` 는 **문서 전체에서 유일**해야 합니다 (`ar1`, `ar2`, …). 한 HTML 안에 여러 그림이 들어가므로 겹치면 화살표가 엉킵니다

### 8.2 검증

작성 후 아래를 확인합니다. `10절 검수 체크리스트`의 빌드 항목과 같습니다.

- SVG 를 XML 로 파싱했을 때 오류가 없는가
- `fill=` / `stroke=` 에 색값이 하드코딩되지 않았는가 (`none`, `url(...)` 은 예외)
- `class=` 에 `style.css` 에 없는 클래스를 쓰지 않았는가
- `role="img"` + `aria-label` 이 모든 SVG 에 있는가

### 9.1 파일 배치

```
study/

└── build/                ← HTML 변환 도구 (단계 무관, 재사용)
    ├── README.md
    ├── build.sh
    ├── template.html
    ├── style.css
    └── filter.lua
```

**파일명 규칙**: `{2자리 단계번호}-{영문-슬러그}.md`
여러 단계를 묶은 문서는 `04-06-vllm-serving.md` 처럼 범위로 씁니다.

**`.md` 가 원본입니다.** HTML 은 언제든 다시 만들 수 있는 산출물이므로 직접 편집하지 않습니다.

### 9.2 마크다운 콜아웃

pandoc `fenced_divs` 문법을 씁니다. `:::` 앞뒤에 빈 줄이 필요합니다.

| 문법 | 라벨 | 용도 |
|---|---|---|
| `::: note` | 개념 보충 | 본문 흐름에서 잠깐 벗어나는 보충 설명 |
| `::: key` | 핵심 | 그 절에서 반드시 남겨야 할 한 문장 |
| `::: calc` | 어림셈 | 공식 + 대입 예 + 틀리는 조건 (4.3 규칙) |
| `::: warn` | 주의 | 오해하기 쉬운 지점, 물리적 위험(전력·발열) |
| `::: later` | 여기까지 — 이후는 뒤 단계 | `[씨앗]` 위임 (3.3 규칙) |
| `::: quote` | 원문 인용 | `../README.md` 또는 Threads 원문 인용 |
| `::: quiz` | 확인 문제 | 7절 |

`::: {.quote data-label="원문 (1단계)"}` 처럼 라벨을 재정의할 수 있습니다.

### 9.3 빌드

```bash
cd study
./build/build.sh 01-hardware
```

자세한 내용은 [`build/README.md`](build/README.md).
